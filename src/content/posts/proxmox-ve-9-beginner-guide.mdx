第一次打开 Proxmox VE，最容易产生的感觉不是“难”，而是**所有熟悉的电脑概念突然多了一层**：

- 一块 SSD 不再直接等于一个盘符，而是先变成 Proxmox 的存储；
- 一张网卡不再直接绑给 Windows，而是先进入 Linux Bridge；
- 物理服务器上又能创建很多“电脑”；
- 一个 256GB 的真实 SSD，甚至可以先创建出 125GB + 300GB 的两块虚拟硬盘。

如果只跟着按钮一路点，很快就会遇到一堆名词：`node`、`vmbr0`、`local`、`local-lvm`、`LVM-Thin`、`CT`、`EFI Disk`、`VirtIO`……

这篇文章不准备把 Proxmox 的菜单逐项翻译一遍，而是先建立一套能长期使用的心智模型，再从一台裸机一路走到可以稳定创建和管理虚拟机。

## 先把 Proxmox 想成一台“虚拟电脑工厂”

Proxmox VE（通常简称 PVE）不是装在 Windows 里面的虚拟机软件。它本身就是安装在裸机上的操作系统和虚拟化管理平台。

官方当前的 Proxmox VE 9.2 基于 Debian 13，核心同时整合了两类虚拟化：

- **KVM / QEMU**：运行完整虚拟机，也就是 VM。
- **LXC**：运行 Linux 容器，也就是 CT。

最重要的结构可以压缩成下面四层：

所以以后看到任何功能，都可以先问一句：**它现在是在操作宿主机、网络、存储，还是 Guest？**

这一个问题能解决大部分新手时期的概念混乱。

## 安装前：先确认你准备牺牲哪块盘

Proxmox 官方 ISO 是裸机安装器。选择某块硬盘作为安装目标时，这块盘上的现有分区和数据会被重新处理，不能把它当成“在现有 Windows 旁边随便加一个软件”。

最简单的学习配置是：

```text
一台闲置电脑
├─ CPU：支持硬件虚拟化
├─ RAM：至少够 PVE + 计划运行的 VM
├─ 系统盘：单独一块 SSD 最省心
└─ 网线：第一次安装强烈建议有线连接
```

进入 BIOS / UEFI 后，确认虚拟化能力已经打开。不同主板名字会有差异，常见名称包括：

- Intel：`Intel Virtualization Technology` / `VT-x`
- AMD：`SVM Mode` / `AMD-V`
- 如果以后需要 PCIe / GPU 直通，还会涉及 `VT-d` / `IOMMU`

入门阶段不需要为了“看起来高级”就上 ZFS、RAID、Ceph。单机学习最重要的是**先把最短链路跑通**。

## 安装 Proxmox VE 9.2：真正需要做的决定只有几个

从官方页面下载当前 Proxmox VE 9.2 ISO，写入 U 盘，再从 U 盘启动安装。

官方当前提供 9.2-1 ISO，安装完成后仍建议通过更新器升级到最新 9.2.x 软件包。因此“ISO 是 9.2-1、后台显示 9.2.2”并不矛盾。

安装向导里重点关注下面几项。

### 1. Target Harddisk：系统到底装到哪块盘

多盘机器最需要谨慎的是这里。

例如本文练习机有：

```text
120GB SSD  ← 选择它安装 PVE
256GB SSD  ← 暂时留空，后面作为 VM 存储
500GB HDD  ← 暂时保留，后面练习新增存储
```

如果无法根据容量分辨硬盘，先记录磁盘型号，不要凭 `/dev/sda`、`/dev/sdb` 的顺序猜。Linux 设备名在不同启动环境下不应该被当成永久身份。

### 2. 文件系统：第一次用，优先简单

安装器会提供 ext4、XFS、ZFS 等选择。对一台单盘系统盘的学习机，**ext4 + 默认 LVM 布局**通常就是最容易理解的起点。

它会让你很快遇到两个默认存储：

```text
local
local-lvm
```

不要急着删。后面会专门解释两者为什么同时存在。

### 3. root 密码和邮箱

这里设置的是 PVE 宿主机的 `root` 管理员密码，不是某台 Windows VM 的密码。

登录 Web UI 时最常见的账号是：

```text
User name: root
Realm: Linux PAM standard authentication
```

界面里经常显示成 `root@pam`。

### 4. Management Network：这里决定以后怎么找到 PVE

安装阶段会要求：

- Management Interface
- Hostname
- IP Address
- Gateway
- DNS Server

家庭局域网最重要的是给 PVE 一个**稳定的管理 IP**。

例如路由器网段是：

```text
路由器：192.168.21.1
网段：  192.168.21.0/24
```

就可以规划：

```text
PVE：     192.168.21.231/24
Gateway： 192.168.21.1
DNS：     192.168.21.1 或其他可用 DNS
```

最好同时在路由器里做 DHCP 保留，或者确保这个地址不在会被 DHCP 随机分出去的范围里，避免未来 IP 冲突。

## 第一次登录：为什么地址后面是 8006

安装完成重启后，屏幕通常会直接显示管理地址，例如：

```text
https://192.168.21.231:8006/
```

这里的 `8006` 是 Proxmox Web 管理服务默认使用的 HTTPS 端口。

浏览器第一次打开通常会提示证书“不安全”。家庭内网新装 PVE 默认使用本机生成的证书，浏览器无法把它追溯到公开受信任的 CA，所以会警告；这不等于你连接的 PVE 本身已经被攻击。

确认地址就是自己刚安装的局域网主机后，可以继续进入。

登录：

```text
用户名：root
密码：安装时设置的 root 密码
Realm：Linux PAM standard authentication
```

进入之后还会看到“没有有效订阅”的提示。**免费版不是阉割版。** Proxmox VE 本身是开源软件，订阅主要对应企业软件源和商业支持。家庭学习完全可以使用官方提供的 `pve-no-subscription` 软件源。

## 网络：理解 vmbr0，比背任何配置命令都重要

很多人第一次看到 PVE 的网络页面，会以为：

> 我的电脑明明只有一张网卡，为什么又出来一个 `vmbr0`？

因为 Proxmox 需要让宿主机和多台虚拟机共享真实网络。

Linux Bridge 可以理解成一台**运行在宿主机里的虚拟交换机**。

默认配置大致会长这样：

```text
物理网线
  ↓
eno1
  ↓
vmbr0  ← PVE 自己的 192.168.21.231
  ├─ VM 100 网卡
  ├─ VM 101 网卡
  └─ CT 102 网卡
```

所以 `vmbr0` 不是 Wi-Fi，也不是“第二张网卡”。它更接近一个软件交换机。

### `/etc/network/interfaces` 到底在写什么

Proxmox 继续使用标准 Linux 网络配置。一个典型的单网卡桥接配置类似：

```text
auto lo
iface lo inet loopback

iface eno1 inet manual

auto vmbr0
iface vmbr0 inet static
    address 192.168.21.231/24
    gateway 192.168.21.1
    bridge-ports eno1
    bridge-stp off
    bridge-fd 0
```

只要理解三件事就够了：

```text
eno1                 = 真实网卡
bridge-ports eno1    = 把真实网卡接进 vmbr0
address / gateway    = PVE 自己通过 vmbr0 使用的网络配置
```

### IP 改错，为什么 Web UI 会“消失”

因为浏览器访问的是 PVE 宿主机的管理 IP。

如果你把：

```text
192.168.21.231
```

改成了一个不属于当前局域网的地址，PVE 并没有坏，只是你的电脑找不到它了。

这也是为什么第一次折腾网络时，最好让机器旁边还有显示器和键盘。Web UI 断了以后，可以直接从本地 Shell 检查：

```bash
ip addr
ip route
cat /etc/network/interfaces
```

GUI 里最常见的修改路径是：

```text
节点 pve
→ 系统
→ 网络
→ 选中 vmbr0
→ 编辑
→ 修改 IPv4/CIDR、Gateway
→ Apply Configuration
```

DNS 则可以在“节点 → 系统 → DNS”里单独检查。PVE 9 默认使用 `ifupdown2`，通过 Web UI 提交的网络修改可以直接 Apply Configuration，不必为了每一次 IP 修改都重启宿主机。

如果你正在远程修改管理 IP，当前浏览器连接本身会断开，这是正常现象。用新地址重新进入即可。

## 防火墙：先知道它有三层，不要第一次就把自己锁在门外

Proxmox 自带防火墙，单机也可以使用。最重要的不是先背规则语法，而是知道规则可能来自不同层级：

```text
Datacenter Firewall   → 整个 PVE 环境的公共规则
Node Firewall         → 只作用于这台 PVE 宿主机
VM / CT Firewall      → 只作用于指定 Guest
```

比如“限制外部访问 PVE 的 SSH”属于宿主机管理面问题；“只允许某台 Ubuntu VM 的 80 / 443”则更适合放在 Guest 层理解。

第一次学习防火墙时，最好保留本地显示器 / 键盘或其他可靠的管理通道。尤其不要在只剩一个远程 Web 会话时，一次性修改管理 IP、SSH 和防火墙规则，否则很容易分不清到底是哪一层把连接切断了。

单机家庭环境也不建议直接把 `8006` 管理端口暴露到公网。需要远程管理时，更适合先通过 VPN / Tailscale 一类受控网络进入家里，再访问 PVE 管理地址。

## 忘了 root 密码：先分清“还能不能进入宿主机”

密码恢复分两个场景。

### 场景 A：你已经有 root Shell

如果当前已经能通过本地控制台、SSH 或其他方式进入 root Shell，修改密码就是标准 Linux 命令：

```bash
passwd
```

或者明确指定：

```bash
passwd root
```

改完以后直接用新密码登录 `root@pam`。

### 场景 B：root 密码彻底忘了，Web / SSH 都进不去

这时需要**物理控制台的启动级恢复**，因为你必须在系统正常登录认证之前拿到本机 root Shell。

最常见的 GRUB 路径是：

```text
1. 重启 PVE
2. 在启动菜单编辑当前 Linux 启动项
3. 临时让系统以 root shell 启动
4. 把根文件系统重新挂成可写
5. passwd root
6. 正常重启
```

在传统 GRUB 启动项里，常见做法是在 Linux 内核启动参数末尾临时追加：

```text
init=/bin/bash
```

让系统这一次直接进入 root shell。它只影响当前这次启动，不是在永久修改 PVE 的启动方式。

进入临时 root Shell 后，核心动作通常是：

```bash
mount -o remount,rw /
passwd root
sync
reboot -f
```

不同安装方式可能使用 GRUB 或 systemd-boot / proxmox-boot-tool，启动菜单的进入方式会不同，因此这里不建议把某一个按键序列当成所有机器都通用的“死命令”。

需要记住的安全事实反而更重要：**对一台没有额外磁盘加密保护的服务器来说，拥有物理控制台和启动介质控制权的人，通常就已经非常接近拥有 root 权限。**

## Tasks、System Log：操作失败以后第一眼应该看哪里

PVE Web UI 底部长期有一个任务日志区域。创建 VM、移动磁盘、备份、恢复、下载模板、更新系统等操作，本质上都会产生 Task。

所以看到一个红色失败状态时，不要只盯着弹窗：

```text
操作失败
  ↓
底部 Tasks / Task History
  ↓
打开具体任务日志
  ↓
看第一条真正的 ERROR
```

如果问题更偏宿主机本身，再进入节点的 `System Log`、`Shell` 或对应服务日志。

这也是 PVE 很适合学习服务器的地方：GUI 负责操作，但底层任务和错误并没有被藏起来。

## 用户、Realm、权限和 TFA：root@pam 不是唯一账号

学习机只有自己使用时，`root@pam` 最方便；但它是宿主机最高权限账号，不应该因此理解成“PVE 所有人都必须共用 root”。

PVE 的登录名通常写成：

```text
user@realm
```

例如 `root@pam` 中，`pam` 就是 Linux PAM Realm。PVE 还可以创建自己的用户、组、角色并通过 ACL 分配权限，也支持两步验证（TFA）。

如果未来让家人或同事只管理某几台 VM，更合理的思路是：

```text
创建独立用户
  ↓
给用户 / 用户组分配角色
  ↓
通过 ACL 限定到某个 VM、CT、Storage 或 Resource Pool
```

`Resource Pool` 也不要和存储池混淆：它主要是**把 VM / CT 等资源做逻辑分组，方便授权和管理**，不是拿来保存虚拟磁盘的地方。

## 磁盘和存储：这是整个 PVE 最值得花时间理解的部分

在 Windows 里，很多人已经习惯：

> 插一块硬盘 → 分区 → 格式化 → 出现 D 盘。

Proxmox 多了一层“存储后端”。

## 两个必须记住的概念：LVM-Thin 和 Directory

如果只准备记两句话，就记下面两句：

<section class="pve-storage-compare" aria-label="LVM-Thin 和 Directory 核心区别">
  <article class="is-thin">
    <span>LVM-THIN</span>
    <strong>虚拟机硬盘池</strong>
    <p>块级存储，重点服务 VM / CT 的虚拟磁盘。支持高效快照和克隆，也支持 Thin Provisioning。</p>
    <small>记忆：专门“切虚拟硬盘”</small>
  </article>
  <article class="is-dir">
    <span>DIRECTORY</span>
    <strong>普通文件盘 / 通用存储</strong>
    <p>文件级存储，可以放 VM 镜像、ISO、CT 模板、备份、Snippets 等多种内容。</p>
    <small>记忆：像普通 Linux 文件目录</small>
  </article>
</section>

更完整一点：

| 能力 | LVM-Thin | Directory |
| --- | --- | --- |
| 主要定位 | VM / CT 虚拟磁盘池 | 通用文件型存储 |
| VM 磁盘 | ✅ | ✅ |
| CT RootFS | ✅ | ✅ |
| ISO | ❌ | ✅ |
| CT 模板 | ❌ | ✅ |
| PVE Backup 文件 | ❌ | ✅ |
| 原生高效 Snapshot | ✅ | 取决于镜像格式；qcow2 可实现 |
| Thin Provisioning | ✅ | 可由 qcow2 等机制实现 |
| 能否直接当普通目录浏览 | 不适合作普通文件盘使用 | ✅ |

这也解释了默认安装为什么经常同时有：

```text
local      → Directory
local-lvm  → LVM-Thin
```

它们不是重复，而是在做不同工作。

## LVM-Thin 为什么能“256GB 创建出 425GB”

本文练习环境里有一个非常直观的实验：

```text
真实 SSD：        256GB

VM 100 disk-0：  125GB
VM 100 disk-2：  300GB
-----------------------
虚拟标称容量：     425GB
```

425GB 已经大于 256GB，但 LVM-Thin 仍然允许创建。

原因就是 **Thin Provisioning（精简配置）**。

普通厚分配更接近：

```text
创建 100GB
≈ 先为它保留 100GB 的真实空间
```

Thin Provisioning 更接近：

```text
告诉 VM：你有 100GB
实际底层：写了多少数据，才逐步消耗多少真实块
```

<section class="pve-board pve-thin" aria-label="LVM-Thin 精简配置示意">
  <header><span>STORAGE MECHANISM</span><strong>“看起来有多大”和“真实写了多少”必须分开</strong></header>
  <div class="pve-thin__numbers">
    <article><span>PHYSICAL</span><strong>256GB</strong><p>真实 SSD 上限</p></article>
    <i>≠</i>
    <article><span>VIRTUAL</span><strong>425GB</strong><p>VM 看到的标称总容量</p></article>
  </div>
  <div class="pve-thin__bars">
    <div><span>125GB 虚拟盘</span><b style={{ '--usage': '32%' }}></b><small>假设实际只写 40GB</small></div>
    <div><span>300GB 虚拟盘</span><b style={{ '--usage': '17%' }}></b><small>假设实际只写 50GB</small></div>
    <div class="is-physical"><span>真实池使用</span><b style={{ '--usage': '35%' }}></b><small>大约 90GB + 元数据等开销</small></div>
  </div>
  <footer><strong>关键风险：</strong>虚拟容量可以超卖，真实容量不能。Thin Pool 真写满以后，Guest 会收到 I/O 错误，甚至可能造成文件系统损坏。</footer>
</section>

所以 LVM-Thin 的正确心智模型不是“凭空变大硬盘”，而是：

> **允许先承诺容量，再按真实写入逐步兑现。**

学习环境可以故意做超额分配体验机制；生产环境则必须持续监控真实池的剩余空间。

## 新增一块 500GB HDD：到底做 LVM-Thin 还是 Directory

第一步不是“创建存储”，而是先确认：**里面的数据还要不要。**

如果不要，才进入擦除 / 重建。

### GUI 创建 Directory 的典型思路

大致过程是：

```text

  ↓

  ↓
擦除旧分区
  ↓

  ↓

  ↓
```

不同 9.2.x 小版本菜单文字可能有细微变化，但底层关系不变：**先让 Linux 有一个可用文件系统和挂载点，再把这个目录注册成 PVE Storage。**

## 为什么 ISO 能放 local，却通常不能放 local-lvm

现在这个问题应该已经很好理解了。

`local` 是 Directory，所以可以有：

```text
ISO Images
CT Templates
Backup
Snippets
甚至 VM Images
```

而 `local-lvm` 是 LVM-Thin，主要内容类型是：

```text
VM images
CT rootdir
```

它不是普通文件目录，所以不能把一个 Windows `.iso` 文件像复制到 D 盘一样塞进去。

上传 ISO 最常见路径：

```text
存储 local
→ ISO Images
→ Upload
```

然后创建 VM 时，从这个存储选择安装镜像。

## 创建第一台虚拟机：不要被十几个参数吓到

点击“创建虚拟机”以后，参数很多，但新手真正要理解的只有几组。

### VM ID 是什么

PVE 用数字标识 Guest，例如：

```text
100 → Windows 10
101 → Ubuntu Server
102 → Home Assistant
```

这个 ID 会进入配置文件名、磁盘卷名、备份名等地方，所以比“显示名称”更基础。

### CPU：不要一开始把所有核心都塞给一台 VM

虚拟 CPU 可以超分，但学习阶段更推荐从实际需求出发。

例如宿主机有 12 核，不代表 Windows VM 一定要直接分 12 核。给 4～8 核跑普通桌面和测试，往往已经足够，而且能给宿主机和其他 VM 留资源。

CPU Type 在单机环境里经常可以考虑 `host`，让 Guest 看到更多真实 CPU 指令集；如果未来要做跨不同 CPU 节点迁移，则需要重新考虑兼容性。本文不进入集群迁移。

### 内存：分配值不等于宿主机可以无限透支

PVE 可以使用 Ballooning 等机制动态管理部分 Guest 内存，但不要把它理解成“内存也可以无风险超卖”。

如果宿主机实际 RAM 被吃光，Linux 仍然要面对内存压力甚至 OOM。

## Windows VM：为什么 VirtIO 这么常见

VirtIO 是面向虚拟化环境的高性能半虚拟化设备模型。

简单理解：

```text
模拟一块老 SATA / IDE 设备
→ Guest 很容易认识，但虚拟化开销更传统

VirtIO
→ Guest 知道自己在虚拟机里，用专门驱动直接配合 Hypervisor
```

因此 Windows 安装里经常需要准备 VirtIO Driver ISO。

一个常见 Windows VM 组合是：

```text
BIOS:          OVMF (UEFI)
Machine:       q35
Disk Bus:      SCSI / VirtIO SCSI
Network:       VirtIO
EFI Disk:      有
TPM:           Windows 11 按需要增加
QEMU Agent:    安装系统后配置
```

如果 Windows 安装器提示“没有磁盘”，而你又使用了 VirtIO / SCSI 虚拟控制器，第一反应应该是：**安装器可能缺少对应 VirtIO 存储驱动，而不是 PVE 没创建磁盘。**

## QEMU Guest Agent：让宿主机真正“认识” Guest

VM 能启动，不代表 PVE 已经能深入了解 VM 内部状态。

QEMU Guest Agent 是安装在 Guest 内部的服务，用来让 PVE 与 Guest 更好地协作，例如：

- 更可靠地获取 Guest IP；
- 发起 Guest 内部关机；
- 配合备份实现更好的文件系统一致性；
- 执行部分 Guest Agent 能力。

它需要两边都准备：

```text
PVE VM 设置里启用 QEMU Guest Agent
+
Guest 系统里安装并运行 qemu-guest-agent
```

只勾 PVE 的开关但 Guest 没装服务，不会凭空产生 Agent 能力。

## 给正在用的 VM 再加一块 300GB 磁盘，需要重启整台 PVE 吗

通常不需要。

添加虚拟硬盘发生在：

```text
VM 100
→ Hardware
→ Add
→ Hard Disk
```

如果 Guest 和所选虚拟控制器支持热插拔，新磁盘甚至可以在虚拟机运行时被发现；即使 Guest 没立即识别，通常也只是重启**这台 VM**，而不是重启整个 Proxmox 宿主机。

Windows 看到新硬盘以后，还要完成 Windows 自己的磁盘初始化：

```text
PVE 创建 300GB 虚拟磁盘
    ↓
Windows 发现“磁盘 1”
    ↓
磁盘管理
    ↓
初始化 GPT
    ↓
新建简单卷
    ↓
格式化 NTFS
    ↓
出现 D: / E:
```

**PVE 创建虚拟磁盘 ≠ Windows 自动创建盘符。**

这是典型的“宿主机层”和“Guest 层”边界。

## 虚拟磁盘还能扩容、移动和拆下，但“删除”要特别谨慎

创建完虚拟机以后，磁盘并不是固定不动的。常见操作包括：

- **Resize Disk**：把虚拟磁盘扩大；
- **Move Storage / Move Disk**：把虚拟磁盘从一个 PVE Storage 移到另一个；
- **Detach**：从 VM 配置里拆下，通常会变成 `Unused Disk`，数据还在；
- **Remove / Delete**：真正删除对应虚拟磁盘数据。

其中扩容最值得先理解：

```text
PVE：125GB → 200GB
       ↓
Guest 只看到“后面多了一段未分配空间”
       ↓
Windows 磁盘管理 / Linux 文件系统
       ↓
继续扩展分区和文件系统
```

所以和“新增第二块盘”一样，PVE 只负责把虚拟硬件变大；Guest 内部怎么使用新增空间，是另一层操作。

反过来缩小磁盘就复杂得多。PVE 的常规 Resize 工作流不支持直接缩小虚拟磁盘，因为还牵涉 Guest 文件系统、分区边界和底层卷。新手阶段把它理解成：**扩容容易，缩容不要靠直接改数字尝试。**

## VM 和 CT 到底选哪个

PVE 不只有虚拟机，还有 LXC Container。

<section class="pve-vm-ct" aria-label="VM 和 LXC Container 对比">
  <article>
    <span>VM · KVM/QEMU</span>
    <strong>像一台完整独立电脑</strong>
    <p>拥有自己的虚拟硬件和 Guest Kernel，可以运行 Windows，也可以运行任意合适的 Linux。</p>
    <small>隔离更完整 · 开销更高 · 兼容性最直观</small>
  </article>
  <article class="is-primary">
    <span>CT · LXC</span>
    <strong>像一个轻量 Linux 系统容器</strong>
    <p>共享 PVE 宿主机的 Linux Kernel，但拥有自己的用户空间、文件系统、网络和进程空间。</p>
    <small>启动快 · 开销低 · 只适合 Linux 容器场景</small>
  </article>
</section>

简单判断：

```text
要 Windows？                    → VM
要完全独立内核？                → VM
要测试不同内核 / 驱动？          → VM
只是跑轻量 Linux 服务？          → 可以考虑 CT
希望最少兼容性变量、先学会 PVE？  → VM 更直观
```

新建 LXC 时还会看到 `Unprivileged Container`。对一般新容器，非特权容器是更安全、更常见的默认方向；只有明确知道自己为什么需要更高宿主权限时，才考虑 privileged container。

还有一个容易混淆的点：**LXC 是系统容器，不等于 Docker。** 如果目标是学习 Docker / Compose 或运行一组应用容器，最省心、隔离边界也更清楚的起点通常是先建一台 Linux VM，再在 VM 里装 Docker。等理解 LXC 的权限、挂载和设备映射以后，再决定是否把某些服务直接放进 CT。

## Snapshot、Backup、Clone：三个看起来相似，目的完全不同

这组概念非常容易混。

<section class="pve-board pve-protection" aria-label="Snapshot Backup Clone 区别">
  <header><span>DATA SAFETY</span><strong>快照不是备份，克隆也不是备份</strong></header>
  <div class="pve-protection__grid">
    <article><span>SNAPSHOT</span><strong>给当前状态打一个“回退点”</strong><p>适合升级、改配置、测试前临时留一个状态。通常仍依赖原存储。</p></article>
    <article class="is-backup"><span>BACKUP</span><strong>生成可独立恢复的备份数据</strong><p>目标应该是原 VM / 原盘坏了以后还能恢复。最好放到独立存储甚至独立设备。</p></article>
    <article><span>CLONE</span><strong>复制出另一台 Guest</strong><p>适合快速创建测试机、模板实例，不解决数据安全问题。</p></article>
  </div>
</section>

最重要的一句话：

> **如果原来的 SSD 整块坏掉，和它放在同一块 SSD 上的 Snapshot 很可能一起消失，所以 Snapshot 不是 Backup。**

### Full Clone 和 Linked Clone

- **Full Clone**：复制出独立磁盘，占用更多空间，但后续不依赖原基础镜像。
- **Linked Clone**：依赖基础镜像，通过差异数据节省空间和时间，对存储能力有要求。

LVM-Thin 原生支持高效 Snapshot / Clone，这也是它非常适合 VM 磁盘池的原因之一。

### Template 是什么

当一台 VM / CT 已经装好系统、驱动、Guest Agent 和基础配置以后，可以把它转换成 Template。

Template 更像“母版”，重点是以后快速克隆，而不是继续把它当普通机器日常启动。

```text
干净 Ubuntu VM
→ 安装 qemu-guest-agent / SSH Key / 基础软件
→ Convert to Template
→ 以后 Clone 出开发机、测试机、临时服务机
```

如果经常重复创建相似系统，Template 比每次重新挂 ISO 安装省事很多。

## 备份放哪里：不要把“有 Backup 按钮”理解成万事大吉

单机学习阶段可以直接把 PVE Backup 存到 Directory 存储，例如前面的 500GB HDD。

```text
256GB SSD
└─ VM 正在运行

500GB HDD
└─ vzdump Backup
```

这已经比“VM 和备份都在同一块 SSD”更有意义。

但如果整台主机被偷、主板烧毁连带磁盘损坏、机箱进水，机内第二块盘也可能一起失效。真正重要的数据最终还是要考虑：

- NAS / NFS；
- Proxmox Backup Server；
- 另一台独立设备；
- 异地备份。

本文只建立边界，不展开 PBS 的完整部署。

### 定时 Backup：真正实用的是让它自动发生

单次手动备份适合学习，但长期使用更应该建立 Backup Job。

在 Web UI 的 Datacenter 级别可以配置备份任务，核心就是四个问题：

```text
备份谁        → 哪些 VM / CT
备份到哪里    → 哪个支持 Backup 的 Storage
什么时候执行  → 每天 / 每周的计划
保留多少份    → Retention / Prune
```

恢复时则从保存 Backup 的存储中选择备份文件并执行 Restore。恢复不是“把快照拨回去”，而是重新根据备份数据构建出 Guest。

学习阶段很值得亲手做一次：

```text
创建一个测试 VM
→ Backup
→ 删除测试 VM
→ Restore 成新的 VM
```

这样会比只看“备份成功”更能确认自己的备份真的可恢复。

## USB、PCIe、GPU 直通：先理解“谁拥有设备”

虚拟机默认拿到的是 PVE 创建的虚拟设备。

直通则是把真实硬件更直接地交给 Guest。

```text
普通虚拟设备
物理硬件 → PVE → 虚拟设备 → VM

Passthrough
物理硬件 → 尽可能直接交给指定 VM
```

### USB Passthrough

最适合入门理解。比如 USB 加密狗、串口设备、U 盘等，可以从 VM → Hardware → Add → USB Device 尝试直通。

### PCIe / GPU Passthrough

复杂度会明显上升，因为它牵涉：

- BIOS / UEFI 的 IOMMU；
- Intel VT-d / AMD IOMMU；
- IOMMU Group；
- vfio；
- 设备是否被宿主机驱动占用；
- Guest 驱动与显卡自身限制。

所以入门阶段只需要知道它存在，不要在还没弄明白存储和网络之前，就把 GPU 直通当成 PVE 的“第一关”。

## PVE 自己关机、VM 关机、浏览器关掉：不是一回事

这是另外一个很基础但很容易混淆的层级问题。

```text
关闭浏览器
→ 只是退出管理界面，PVE 和所有 VM 继续运行

关闭 VM 100
→ 只关闭这一台 Guest

关闭节点 pve
→ 整台物理宿主机关机，所有 Guest 都会受到影响
```

VM 还可以配置：

- Start at boot：宿主机启动后自动启动；
- Start / Shutdown order：控制多台 Guest 的启动和关机顺序；
- Startup delay：避免所有虚拟机同时抢资源。

例如：

```text
PVE 启动
  ↓
先启动软路由 / 基础服务
  ↓ 20s
再启动数据库
  ↓ 20s
最后启动业务应用
```

单机 Homelab 很快就会用到这些设置。

### 用户和权限：root@pam 不是唯一登录方式

学习机用 `root@pam` 最直接，但 PVE 本身有完整的用户、Realm、Role 和 ACL 权限体系。

可以先建立这个概念：

```text
User   = 谁在登录
Role   = 允许做什么
ACL    = 在哪个对象上允许做这些事
Realm  = 账号从哪里认证
```

例如家庭环境里，可以保留 root 作为救援账号，再给日常管理创建单独用户。即使只有一台节点，这也比长期共享 root 密码更清晰。

### 防火墙：先理解层级，再打开规则

PVE Firewall 可以作用在多个层级：

```text
Datacenter
  ↓
Node
  ↓
VM / CT
```

上层是统一策略，下层可以继续补充 Guest 自己的规则。第一次学习时不要在远程环境里“边猜边开”，尤其是管理端口和 SSH；一旦把自己的管理流量拦掉，最后还是要回物理控制台救援。

### NAS 存储：Directory 不是唯一的文件型存储

如果家里已经有 NAS，PVE 可以直接添加 NFS 或 CIFS/SMB 存储。它们在使用体验上很像远程的 Directory：可以根据后端能力配置 ISO、模板、Backup、VM Image 等 Content。

典型用途是：

```text
PVE 本地 SSD
→ 跑 VM

NAS
→ 存 Backup / ISO / Template
```

这样即使 PVE 主机里的本地 SSD 故障，备份仍然在另一台设备上。

### 模板和 Cloud-Init：当你开始重复创建 Linux VM

第一台 Ubuntu 手动安装完全合理。到了第三、第四台，如果每次都重复设置用户名、SSH Key、IP 和软件源，就可以开始使用：

```text
准备一台基础 VM
→ 安装 qemu-guest-agent / cloud-init
→ Convert to Template
→ Clone
→ 填写 Cloud-Init 参数
→ 启动成为一台新 VM
```

它解决的是“重复部署 Guest”的问题，而不是 PVE 入门必须掌握的第一步。

### 看磁盘健康：Storage 正常不代表物理盘健康

存储页面告诉你“这个 Storage 还能不能用、容量还剩多少”；磁盘页面则更接近底层硬件。

例如：

```text
节点 → 磁盘
→ 型号 / 容量 / 分区
→ S.M.A.R.T.
```

出现 I/O 错误、掉盘、异常慢速时，不要只盯着 VM。继续向下检查真实 SSD / HDD 的 S.M.A.R.T.、系统日志和线材连接，才是正确排查方向。

## 免费版怎么更新：企业仓库报 401 不代表系统坏了

Proxmox VE 软件本身免费开源，但 Enterprise Repository 需要有效订阅。

无订阅学习机应该使用官方的 **No-Subscription Repository**。

PVE 9 使用 Debian 13 `trixie`。当前官方文档给出的 no-subscription 配置采用 deb822 格式，例如：

```text
Types: deb
URIs: http://download.proxmox.com/debian/pve
Suites: trixie
Components: pve-no-subscription
Signed-By: /usr/share/keyrings/proxmox-archive-keyring.gpg
```

文件通常放在：

```text
/etc/apt/sources.list.d/proxmox.sources
```

对普通用户，更推荐直接在 Web UI 的 Repository 页面检查：

```text
有企业订阅
→ pve-enterprise

没有企业订阅
→ 禁用无法使用的 enterprise repository
→ 启用 pve-no-subscription
```

然后可以通过 GUI 更新，也可以在 Shell 中：

```bash
apt update
apt dist-upgrade
```

No-Subscription 软件源并不是“破解源”，它就是 Proxmox 官方提供给无订阅用户的公开软件源；区别在于企业仓库经过更严格的验证，并包含商业支持体系。

## Shell 里最值得新手认识的 8 个命令

GUI 优先并不等于完全不碰 Shell。真正排错时，下面这些命令非常高频：

```bash
# PVE 版本
pveversion -v

# 网卡 / IP
ip addr

# 默认路由
ip route

# 网络配置
cat /etc/network/interfaces

# 真实磁盘与分区
lsblk

# PVE 已注册存储及容量
pvesm status

# LVM 逻辑卷
lvs

# 当前系统磁盘空间
df -h
```

它们正好对应四层心智模型：

```text
pveversion       → Host
ip addr / route  → Network
lsblk / lvs      → Physical / LVM
pvesm status     → PVE Storage
```

## 哪些东西这篇文章故意没有深入

Proxmox 的功能远不止本文这些。继续往后会遇到：

```text
单机 PVE
│
├─ ZFS / RAID / SMART / 磁盘故障治理
├─ VLAN / Bond / SDN / 多网桥
├─ PCIe / GPU Passthrough
├─ NFS / SMB / iSCSI / NAS
├─ Proxmox Backup Server
│
└─ 多节点之后
   ├─ Cluster
   ├─ Migration
   ├─ HA
   └─ Ceph
```

其中 **Ceph 不是“给单机多一块硬盘用的功能”**。它是面向分布式存储集群的体系；一台学习机看到左侧有 Ceph 菜单，不代表你需要配置它。

同样，HA、动态负载均衡等 Proxmox VE 9.2 新能力主要服务多节点环境。单机用户先把网络、存储、Guest 和备份理解清楚，收益远远更高。

到这里，再回头看 Proxmox 左侧的“数据中心、节点、虚拟机、存储”，它们就不再是一堆菜单，而是同一套系统的不同层级。

真正值得先掌握的也不是所有高级参数，而是四句话：

1. **Node = 一台真实的 PVE 宿主机。**
2. **vmbr0 = 把宿主机和 Guest 接到真实网络的软件交换机。**
3. **LVM-Thin = 虚拟机硬盘池；Directory = 普通文件盘 / 通用存储。**
4. **物理硬盘、PVE Storage、VM 虚拟硬盘永远分三层理解。**

这四个关系稳了，后面的 ZFS、NAS、Passthrough、Cluster 和 Ceph 才是“增加能力”；否则只是在继续增加名词。
