自动化 Agent 最容易失控的原因，不是模型不够聪明，而是任务、状态、工具权限和失败处理混在了一起。这篇文章把它们拆成一套执行控制系统：**先分流，再记账；先授权，再执行；每一步都可验证、可追踪、可续接。**

## 先让任务走进正确的执行通道

同一个“帮我处理一下”的请求，可能只是一次可逆的小修，也可能会跨多个阶段、产生外部副作用。先决定流程重量，才能避免小任务被流程拖慢，也避免大任务靠对话记忆硬撑。

<AgentWorkflowDecisionTree />

这不是审批流程。它只回答一个问题：**为下一次继续执行，必须留下多少状态？** 能局部验证的任务直接做；有少量协作但不依赖长期状态的任务写 brief；只有必须分阶段验收、会中断续接或需要稳定记录风险与下一步时，才建立 `TASK.md`。文件多不等于一定要建状态文件。

## 用状态账本让大任务可以暂停后继续

`TASK.md` 不是聊天记录，也不是把每个念头都存下来。它是**执行状态的事实来源**：记录目标、当前位置、下一步和仍未关闭的风险。续接时仍要读取当前代码、项目规则和 `git diff`，确认外部事实没有在任务中断期间变化。

小改一个函数、删几行规则或补一处文案时，不要为了“规范”新建状态文件。状态文件本身也有维护成本；它只应在任务会中断、会分批或会被他人接手时出现。

## 把模型判断和工具副作用放在两层

Agent 可以规划、比较和解释，但工具应该只做边界清晰的确定动作。真正可维护的设计，不是把工具包装得越来越深，而是让每次调用都回答四件事：谁授权、输入是什么、写到了哪里、结果怎样验证。

<section class="agent-control-board agent-authority-board" aria-label="模型与工具职责边界">
  <header class="agent-board-head"><div><span>03 · AUTHORITY SPLIT</span><h3>判断可以灵活，执行必须可追踪</h3></div><p>把“思考”和“产生副作用”拆开，才能定位失败，也能限制自动化越权。</p></header>
  <div class="agent-authority-grid">
    <article class="agent-authority-card agent-authority-model"><span>AGENT LAYER</span><h4>模型负责形成可审查的计划</h4><ul><li>归纳输入和上下文</li><li>选择流程和工具</li><li>标出不确定性与人工确认点</li></ul><p>输出应是明确意图，而不是隐式副作用。</p></article>
    <div class="agent-authority-handoff"><b>意图</b><i>↓</i><b>参数</b><i>↓</i><b>授权</b></div>
    <article class="agent-authority-card agent-authority-tool"><span>TOOL LAYER</span><h4>工具负责可验证的原子动作</h4><ul><li>读取、写入、点击、发送、落盘</li><li>返回结构化结果与错误</li><li>保留动作对象和执行时间</li></ul><p>工具不替模型猜业务，也不静默吞掉异常。</p></article>
  </div>
  <div class="agent-permission-strip"><span>所有副作用：记录动作并验证真实结果</span><span>既有授权内：可修改文件或本地落盘，不重复请求确认</span><span>额外确认：越权、外部发送、批量高风险或不可逆操作</span></div>
</section>

例如，网页自动化不要只返回“已完成”。它至少应返回目标元素、实际动作、页面反馈和异常信息；文件写入也要返回路径、变更摘要和可复核的结果。这样日志才是在描述事实，而不是在给成功贴标签。

## 每次执行都要形成一条可复盘的闭环

执行闭环的关键不是增加更多步骤，而是让每个阶段的输出成为下一阶段的输入。结果未验证时，它只是候选结果，不能被当作完成；需要人工判断时，工作流必须显式停在闸门前。

<section class="agent-control-board agent-loop-board" aria-label="Agent 执行闭环">
  <header class="agent-board-head"><div><span>04 · EXECUTION LOOP</span><h3>从请求到记录，不留“已经做了什么”的黑箱</h3></div><p>这条轨道可以用于浏览器、文件、数据处理和内容生成等不同工具。</p></header>
  <div class="agent-loop-track">
    <article><b>01</b><strong>读取</strong><span>目标、上下文、约束</span></article><i>→</i>
    <article><b>02</b><strong>计划</strong><span>动作、边界、预期结果</span></article><i>→</i>
    <article><b>03</b><strong>执行</strong><span>调用一个可定位的工具动作</span></article><i>→</i>
    <article><b>04</b><strong>验证</strong><span>检查真实结果，而非调用成功</span></article><i>→</i>
    <article class="agent-loop-record"><b>05</b><strong>记录</strong><span>写回状态、日志和下一步</span></article>
  </div>
  <div class="agent-loop-check"><span>验证不通过</span><b>回到计划，缩小假设或切换工具</b><span>验证通过</span><b>记录事实，再进入下一阶段</b></div>
</section>

一个实用的日志条目不必很长：`任务 ID → 工具动作 → 对象 → 结果 → 验证证据 → 下一步`。保持格式稳定，才便于后续检索、排错和人工复核。

## 失败不是结束，而是一次有分级的升级

错误信息不等于失败处理。真正的失败处理要先隔离影响，再决定能否重试、能否回退，还是应该把带上下文的判断交给人。批量任务尤其不能把“一个失败”扩大成“整批状态不明”。

<section class="agent-control-board agent-failure-board" aria-label="Agent 失败升级策略">
  <header class="agent-board-head"><div><span>05 · FAILURE ESCALATION</span><h3>先守住状态，再决定重试、回退或交给人</h3></div><p>每条失败路径都要有明确落点，避免异常被装饰器、重试循环或模糊提示吞掉。</p></header>
  <div class="agent-failure-grid">
    <article class="agent-failure-start"><span>事件</span><strong>工具返回异常或结果验证失败</strong><p>先记录任务、对象、错误和已完成范围。</p></article>
    <article><span>可重试？</span><strong>短暂网络、页面加载、限流</strong><p>有限次数重试；每次记录条件与结果。</p><b class="agent-failure-tag agent-failure-retry">重试</b></article>
    <article><span>可回退？</span><strong>已授权且可逆的局部动作</strong><p>按明确对象执行回退并再次验证，不扩大修改或删除范围。</p><b class="agent-failure-tag agent-failure-rollback">回退</b></article>
    <article><span>需人工？</span><strong>业务判断、越权或不可逆影响</strong><p>带上证据、选项和建议，而不是只报错。</p><b class="agent-failure-tag agent-failure-review">人工确认</b></article>
  </div>
  <div class="agent-isolation-rule"><b>批量任务的隔离原则</b><span>逐项处理就逐项落盘；整批处理就明确批次边界。失败项必须可重放，成功项不能因重试而重复执行。</span></div>
</section>

最终，工作流的可靠性不来自“永不失败”，而来自失败时仍能说清：影响到什么、留下了什么状态、下一步由谁处理。

<div class="agent-summary"><span>TAKEAWAY</span><strong>把自动化当成一套执行系统：任务有路由，状态有账本，工具有权限，结果有证据，失败有出口。</strong></div>
