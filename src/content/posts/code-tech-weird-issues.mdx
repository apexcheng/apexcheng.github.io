## 01｜API 分页时 `total` 变化，不一定意味着接口漏单

### 现象

使用管易 C-ERP 的发货单接口 `gy.erp.trade.deliverys.get`，按 `start_modify_date / end_modify_date` 限定修改时间，再通过 `page_no / page_size` 分页查询，每页读取 100 条。

一次实际同步中，同一时间窗口的前面几页返回 `total = 1027`，后面的页面却返回 `total = 1023`。同步程序把 `total` 变化视为窗口不完整，自动重试两次后仍未通过校验，导致增量同步无法继续推进。

**已确认的是总数变化和校验失败，并未确认有订单实际漏读，更不能据此认定漏了 4 单。**

### 原理

普通的页码分页可以理解为下面的偏移查询：

```sql
-- 每页 100 条，仅用于解释 OFFSET 分页原理
LIMIT 100 OFFSET 0;   -- 第 1 页
LIMIT 100 OFFSET 100; -- 第 2 页
LIMIT 100 OFFSET 200; -- 第 3 页
```

关键在于：**每一页可能都是对当时数据的重新查询，而不是持续读取第一页生成的固定快照。** 上面只是通用原理示意，并不代表已经确认管易接口内部使用这些 SQL。

两次请求之间，如果订单新增、修改、作废，符合时间范围的记录集合就可能变化；接口的统计、排序或内部处理也可能影响结果。目前无法仅凭 `total` 变化判断是哪种原因。

按**最后修改时间**同步尤其需要关注这个问题：旧订单发生新的修改后，也可能移出原来的查询窗口。但使用修改时间又很必要，因为旧订单的发货状态、物流信息等发生变化时，同步程序仍需要捕获。

### 一个简单例子

假设每页读取 3 条，且查询顺序固定：

```text
第一次查询：A B C D E F
第 1 页 OFFSET 0 → A B C

此时 B 退出查询范围，剩下：A C D E F
第 2 页 OFFSET 3 → E F

拼接结果：A B C E F
漏读风险：D 没有出现在拼接结果中
```

虽然两页返回的数据各自都可能是正确的，但**客户端拼接后的结果未必完整**。如果数据在前面插入，也可能出现跨页重复。

这说明了潜在风险，并不表示上述实际同步已经发生了同样的漏单。

### 处理建议

- **缩小时间窗口**：减少单个窗口跨越的页数，降低分页期间数据变化的影响。
- **重叠回查 + 幂等更新**：每次回看一小段已同步时间，按稳定业务 ID 更新记录，让重复读取安全，并为遗漏提供后续补取机会。
- **重复查询并做一致性校验**：除了关注 `total`，还要核对记录 ID、去重后的数量及跨次查询差异；仅仅总数相同也不能证明没有漏单。
- **优先使用稳定分页机制**：如果 API 提供固定快照或稳定游标，优先采用；如果只有页码分页，就需要客户端自行处理动态数据的风险。
- **谨慎放宽 `total` 校验**：经过重复回查或其他可信校验后，可以允许已验证的总数波动；不能一看到变化就失败，也不能无条件忽略变化。

### 最终经验

**`total` 变化是“分页结果可能不一致”的信号，不是“实际漏了多少单”的证据。**

要分别判断两件事：**单次 API 返回是否正确**，以及**多次分页拼接后是否完整**。真正可靠的增量同步，不能只依赖每页请求成功，也不能只依赖某一次的 `total`。
