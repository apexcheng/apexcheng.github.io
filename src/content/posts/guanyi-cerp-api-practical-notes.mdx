## 1. 接入概览

### 1.1 请求地址

```text
POST http://api.guanyierp.com/rest/erp_open
Content-Type: application/json
```

### 1.2 公共请求字段

| 字段 | 说明 | 状态 |
| --- | --- | --- |
| `appkey` | 应用 Key | 已验证 |
| `sessionkey` | 会话凭证 | 已验证 |
| `method` | API 方法名 | 已验证 |
| `sign` | 请求签名 | 已验证 |
| 业务参数 | 各接口自己的查询参数 | 视接口而定 |

真实 `appkey`、`sessionkey`、`secret` 不应写入源码仓库、公开文档或日志。

### 1.3 签名算法

当前已验证的签名方式：

```python
import hashlib
import json

def make_sign(payload: dict, secret: str) -> str:
    data = {key: value for key, value in payload.items() if key != "sign"}
    json_text = json.dumps(
        data,
        ensure_ascii=False,
        separators=(",", ":"),
    )
    raw = f"{secret}{json_text}{secret}"
    return hashlib.md5(raw.encode("utf-8")).hexdigest().upper()
```

签名时要保证：

- `sign` 本身不参与签名。
- 参与签名的业务参数与最终实际发送的参数一致。
- JSON 序列化格式保持一致；字段类型、空值或序列化方式变化都可能导致签名不同。

### 1.4 最小请求结构

```json
{
  "appkey": "<APP_KEY>",
  "sessionkey": "<SESSION_KEY>",
  "method": "gy.erp.new.stock.get",
  "page_no": 1,
  "page_size": 100,
  "sign": "<SIGN>"
}
```

## 2. 通用响应与错误处理

不要只判断 HTTP 状态码。C-ERP 可能在 HTTP 请求成功时返回业务错误。

建议统一检查：

```text
success
errorCode
errorDesc
subErrorCode
subErrorDesc
```

处理原则：

| 条件 | 建议 |
| --- | --- |
| HTTP 请求失败 | 记录网络异常并按调用策略重试 |
| HTTP 成功但 `success != true` | 按业务失败处理 |
| 返回分页数据 | 同时校验 `total` 和实际收取数量 |
| 返回未知字段 | 先保留原始响应，再决定是否映射 |
| 资料与真实响应不一致 | 以真实租户响应为准 |

## 3. 分页与完整性规范

多个 C-ERP 列表接口使用：

```text
page_no
page_size
total
```

全量或历史同步不应以“某一页请求成功”作为批次成功条件。

建议至少检查：

1. `total` 是否在分页期间发生漂移。
2. 是否出现重复页或重复业务主键。
3. 是否在尚未收齐 `total` 前提前返回空页。
4. 是否异常提前返回短页。
5. 最终接收数量是否与 `total` 一致。
6. 是否超过预设最大页数保护。

## 4. 时间字段与数据区

C-ERP 中“创建时间、修改时间、发货时间”不是同一语义。

| 时间 | 适合用途 |
| --- | --- |
| 创建时间 | 判断单据何时产生 |
| 修改时间 | 增量捕获已存在单据的后续变化 |
| 发货时间 | 按真实发货事实统计与历史回填 |

发货单还存在 **近期数据区 / 历史数据区**：

```text
近期发货单
→ gy.erp.trade.deliverys.get

历史发货单
→ gy.erp.trade.deliverys.history.get
```

这两个接口不是简单的参数别名，真实租户已经验证存在明确的数据分层。

## 5. 店铺接口

### 5.1 店铺查询

**Method**

```text
gy.erp.shop.get
```

**用途**

获取店铺基础信息，并在只有店铺名称或昵称时解析真正的 `shop_code`。

**已确认返回字段**

```text
id
code
name
nick
```

**关键规则**

```text
shop_code != shop_id
```

订单相关接口需要店铺编码时，应使用实际 `code`，不能把页面或其它系统中的店铺 ID 直接当成 `shop_code`。

**状态：资料确认**

### 6.1 商品 / SKU / 组合品查询

**Method**

```text
gy.erp.items.get
```

**用途**

查询商品主数据、SKU、条码和组合品 / BOM 关系。

**已确认请求参数**

| 参数 | 说明 |
| --- | --- |
| `page_no` | 页码 |
| `page_size` | 每页数量 |
| `start_date` | 修改时间起点 |
| `end_date` | 修改时间终点 |
| `code` | 指定商品代码 |

**已确认返回内容**


**状态：已验证**

## 7. 库存接口

### 7.1 当前库存查询

**Method**

```text
gy.erp.new.stock.get
```

**用途**

按仓库、商品或 SKU 查询当前库存。

**已确认请求参数**

| 参数 | 说明 |
| --- | --- |
| `page_no` | 页码 |
| `page_size` | 每页数量 |
| `warehouse_code` | 仓库编码 |
| `item_code` | 可选，商品代码 |
| `item_sku_code` | 可选，SKU / 规格代码 |

**主要返回结构**

```text

```

**完整性要求**

全量库存只有在所有分页完整收齐后，才适合作为新的可信库存快照。重复页、提前空页、提前短页、`total` 漂移或页数超过保护上限都应视为不完整批次。

**状态：已验证**

## 10. 近期 / 历史发货单差异

这是当前最重要的接口边界。

| 能力 | `deliverys.get` | `deliverys.history.get` |
| --- | --- | --- |
| 数据区 | 近期 | 历史 |
| 修改时间查询 | 已验证支持 | 已验证不支持 |
| 发货时间查询 | 支持 | 必须使用 |
| `warehouse_code` 服务端筛选 | 已验证支持 | 已验证无效 / 不应依赖 |
| `detail_flag=true` | 已验证 | 已验证 |
| `del=0/1` | 已验证支持 | 已验证不能照搬 |
| 定向按 `code` | 可用 | 已验证可用 |
| 适合用途 | 持续增量、状态变化 | 历史回填 |

### 10.1 数据分层

真实租户定向验证结果：

```text
较老发货单
deliverys.get          → 0
deliverys.history.get  → 1

近期发货单
deliverys.get          → 1
deliverys.history.get  → 0
```

因此：

> `deliverys.get` 返回成功且 `total=0`，不能单独证明历史数据不存在。

### 10.2 归档边界

实测结果与“约一周后进入历史区”的外部案例相符，但不应把边界硬编码为精确 `7 × 24` 小时。

推荐：

```text
近期区与历史区允许少量重叠查询
→ 以发货单 code / 明细 id 做幂等合并
```

### 10.3 历史接口的仓库过滤

真实请求中，即使给历史接口额外传入 `warehouse_code`，仍会返回多个仓库。

因此历史数据应按：

```text
查询完整历史窗口
→ 客户端按 warehouse_code 过滤
→ 再进入后续业务处理
```

不能假设历史接口会服务端过滤仓库。

### 10.4 历史接口不能使用修改时间做增量

仅向历史接口传：

```text
start_modify_date
end_modify_date
```

真实响应：

```text
PARAM ERR 发货开始时间必填
```

同时传发货时间和修改时间时，也没有观察到修改时间筛选效果。

结论：

```text
deliverys.history.get
→ 以 start_delivery_date / end_delivery_date 为查询时间
→ 不承担近期接口的“按修改时间捕获后续状态变化”职责
```

### 10.5 历史接口的作废状态

`deliverys.get` 已验证支持：

```text
del = 0
del = 1
```

`deliverys.history.get` 的已查资料中没有对应 `del` 参数。真实请求追加 `del=1` 后，也没有观察到筛选效果。

当前结论：

- 不应把近期接口的正常单 / 作废单双流查询直接复制到 history。
- 历史单归档后再次发生取消或作废时，最终补偿机制仍属于 **待验证项**。

## 11. 历史发货接口分页验证

历史接口已经完成过一个完整自然日的多页只读验证。

为避免暴露业务规模，公开文档只保留完整性结论：

| 检查项 | 结果 |
| --- | --- |
| 所有分页是否收齐 | 通过 |
| 发货单号是否重复 | 未发现 |
| 分页期间 `total` 是否漂移 | 未发现 |
| `details.id` 是否缺失 | 未发现 |
| `details.qty` 是否缺失 | 未发现 |
| `detail_flag=true` 是否返回商品明细 | 通过 |
| 是否同时返回多个仓库 | 是 |

该验证说明历史接口可以作为商品级历史发货事实来源，但不代表所有取消 / 作废边界已经验证完成。

## 14. 推荐的数据采集职责

<div class="cerp-doc-flow" role="group" aria-label="C-ERP 数据采集职责">
  <section>
    <b>近期增量</b>
    <code>gy.erp.trade.deliverys.get</code>
    <span>按修改时间获取新增和后续变化</span>
  </section>
  <i>+</i>
  <section>
    <b>历史回填</b>
    <code>gy.erp.trade.deliverys.history.get</code>
    <span>按发货时间拆分历史窗口</span>
  </section>
  <i>→</i>
  <section>

    <code>code / details.id</code>
    <span>幂等合并并做业务过滤</span>
  </section>

接口职责应保持分离：

- 近期接口负责持续捕获修改、取消和作废。
- 历史接口负责已归档发货事实。
- 历史查询后由客户端执行仓库过滤。
- 重叠区间通过业务主键幂等去重，而不是依赖精确归档时间点。

## 16. 当前待验证项

目前仍不应下结论的部分：

- 历史发货单归档后的取消 / 作废如何被稳定重新发现。
- 近期 / 历史数据区的精确切换时刻是否固定。
