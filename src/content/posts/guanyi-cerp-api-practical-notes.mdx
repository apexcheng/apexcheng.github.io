## 1. 接入概览

### 1.1 请求地址

```text
POST http://api.guanyierp.com/rest/erp_open
Content-Type: application/json
```

### 1.2 公共请求字段

| 字段 | 说明 | 状态 |
| --- | --- | --- |
| `appkey` | 应用 Key | 已验证 |
| `sessionkey` | 会话凭证 | 已验证 |
| `method` | API 方法名 | 已验证 |
| `sign` | 请求签名 | 已验证 |
| 业务参数 | 各接口自己的查询参数 | 视接口而定 |

真实 `appkey`、`sessionkey`、`secret` 不应写入源码仓库、公开文档或日志。

### 1.3 签名算法

当前已验证的签名方式：

```python
import hashlib
import json

def make_sign(payload: dict, secret: str) -> str:
    data = {key: value for key, value in payload.items() if key != "sign"}
    json_text = json.dumps(
        data,
        ensure_ascii=False,
        separators=(",", ":"),
    )
    raw = f"{secret}{json_text}{secret}"
    return hashlib.md5(raw.encode("utf-8")).hexdigest().upper()
```

签名时要保证：

- `sign` 本身不参与签名。
- 参与签名的业务参数与最终实际发送的参数一致。
- JSON 序列化格式保持一致；字段类型、空值或序列化方式变化都可能导致签名不同。

### 1.4 最小请求结构

```json
{
  "appkey": "<APP_KEY>",
  "sessionkey": "<SESSION_KEY>",
  "method": "gy.erp.new.stock.get",
  "page_no": 1,
  "page_size": 100,
  "sign": "<SIGN>"
}
```

## 2. 通用响应与错误处理

不要只判断 HTTP 状态码。C-ERP 可能在 HTTP 请求成功时返回业务错误。

建议统一检查：

```text
success
errorCode
errorDesc
subErrorCode
subErrorDesc
```

处理原则：

| 条件 | 建议 |
| --- | --- |
| HTTP 请求失败 | 记录网络异常并按调用策略重试 |
| HTTP 成功但 `success != true` | 按业务失败处理 |
| 返回分页数据 | 同时校验 `total` 和实际收取数量 |
| 返回未知字段 | 先保留原始响应，再决定是否映射 |
| 资料与真实响应不一致 | 以真实租户响应为准 |

## 3. 分页与完整性规范

多个 C-ERP 列表接口使用：

```text
page_no
page_size
total
```

全量或历史同步不应以“某一页请求成功”作为批次成功条件。

建议至少检查：

1. `total` 是否在分页期间发生漂移。
2. 是否出现重复页或重复业务主键。
3. 是否在尚未收齐 `total` 前提前返回空页。
4. 是否异常提前返回短页。
5. 最终接收数量是否与 `total` 一致。
6. 是否超过预设最大页数保护。

## 4. 时间字段与数据区

C-ERP 中“创建时间、修改时间、发货时间”不是同一语义。

| 时间 | 适合用途 |
| --- | --- |
| 创建时间 | 判断单据何时产生 |
| 修改时间 | 增量捕获已存在单据的后续变化 |
| 发货时间 | 按真实发货事实统计与历史回填 |

发货单还存在 **近期数据区 / 历史数据区**：

```text
近期发货单
→ gy.erp.trade.deliverys.get

历史发货单
→ gy.erp.trade.deliverys.history.get
```

这两个接口不是简单的参数别名，真实租户已经验证存在明确的数据分层。

## 5. 店铺接口

### 5.1 店铺查询

**Method**

```text
gy.erp.shop.get
```

**用途**

获取店铺基础信息，并在只有店铺名称或昵称时解析真正的 `shop_code`。

**已确认返回字段**

```text
id
code
name
nick
```

**关键规则**

```text
shop_code != shop_id
```

订单相关接口需要店铺编码时，应使用实际 `code`，不能把页面或其它系统中的店铺 ID 直接当成 `shop_code`。

**状态：已验证**（本租户已实际使用 `gy.erp.shop.get` 的 `shops[].code`、`shops[].name` 核实历史订单归属）

## 7. 库存接口

### 7.1 当前库存查询

**Method**

```text
gy.erp.new.stock.get
```

**用途**

按仓库、商品或 SKU 查询当前库存。

**已确认请求参数**

| 参数 | 说明 |
| --- | --- |
| `page_no` | 页码 |
| `page_size` | 每页数量 |
| `warehouse_code` | 仓库编码 |
| `item_code` | 可选，商品代码 |
| `item_sku_code` | 可选，SKU / 规格代码 |

**主要返回结构**

```text
total
stocks[]
```

**完整性要求**

全量库存只有在所有分页完整收齐后，才适合作为新的可信库存快照。重复页、提前空页、提前短页、`total` 漂移或页数超过保护上限都应视为不完整批次。

**状态：已验证**

## 8. 订单接口

订单接口与历史发货接口需要**组合使用**，不能把四种方法理解成等价的订单号查询。以下流程适用于“已知完整平台订单号，需要确认订单归属并提取商品型号”的定向查询；批量同步全部订单或发货事实另当别论。

| 方法 | 实测用途 | 数据来源 | 状态 |
| --- | --- | --- | --- |
| `gy.erp.trade.get` | 按平台订单号查询当前订单与 ERP 内部单号 | 当前订单 | 已验证 |
| `gy.erp.trade.history.get` | 当前订单未命中时补查历史单号 | 历史订单 | 已验证 |
| `gy.erp.trade.detail.get` | 用 ERP 内部 `code` 获取当前订单商品详情 | 当前订单详情 | 已验证 |
| `gy.erp.trade.deliverys.history.get` | 用历史 ERP 内部 `code` 定向获取历史发货商品 | 历史发货单 | 已验证（本租户） |

### 8.1 当前订单查询

**Method**：`gy.erp.trade.get`

**已实测请求参数**：

| 参数 | 说明 |
| --- | --- |
| `platform_code` | 完整平台订单号，不能只传订单尾号 |
| `page_no` / `page_size` | 分页参数，需核对返回 `total` |
| `shop_code` | 可选，真实 ERP 店铺编码，不能用 `shop_id` 代替 |

真实列表响应包含 `total`、`orders[]`，订单元素含 `code`、`createtime`、`modifytime`、`dealtime`、`paytime` 等。**`orders[].code` 是 ERP 内部单据编号，不等同于 `platform_code`；订单列表本身不保证包含商品明细。**

此外已实测日期窗口参数 `start_date`、`end_date`、`date_type=1`。但日期窗口中出现的单据，其 `createtime` 可能落在窗口之外（例如后续重建的单据）；不能仅凭时间参数推断订单年龄和归档位置。

**状态：已验证**

### 8.2 历史订单查询

**Method**：`gy.erp.trade.history.get`

已实测使用 `platform_code`、`page_no`、`page_size`，还可以使用真实 `shop_code` 做归属核对。返回 `total` 与 `orders[]`；`orders[].code` 是进一步获取历史发货明细的重要内部编号。

**历史接口不是“包含所有订单”的总接口。** 近期一至数天内的部分订单在 `trade.get` 能命中，但 `trade.history.get` 返回 `total=0`。有些较老平台订单却同时出现在两种接口中，且两边对应的 ERP 内部单号不同。

一个 `platform_code` 可能对应多个 ERP 内部 `code`。不得默认为只有一条，更不能在归属未核实时把第一条当成整笔订单。

**状态：已验证**

### 8.3 当前订单详情查询

**Method**：`gy.erp.trade.detail.get`

传入 `code = trade.get` 返回的 `orders[].code`，即 ERP 内部单据编号；**不能直接把平台订单号当成 `code`**。

成功时返回 `orderDetail`，已实测关键字段：

```text
orderDetail.code
orderDetail.platform_code
orderDetail.shop_code
orderDetail.shop_name
orderDetail.createtime
orderDetail.details[].item_code
orderDetail.details[].is_gift
```

真实租户的部分旧订单即使已由 `trade.history.get` 找到，再请求普通订单详情依然是 **`orderDetail = null`**。这不等于历史商品不存在，应考虑历史发货明细。

**状态：已验证**

### 8.4 推荐的定向查询顺序

```text
完整平台订单号
  └─ ① gy.erp.trade.get（platform_code）
       ├─ 当前订单存在
       │    └─ ② gy.erp.trade.detail.get（ERP 内部 code）
       │         └─ 核对 platform_code / 店铺，提取 details
       └─ 当前订单未找到
            └─ ③ gy.erp.trade.history.get（platform_code）
                 └─ 确认历史 ERP 内部单号和店铺归属
                      └─ ④ gy.erp.trade.deliverys.history.get
                           （ERP 内部 code + detail_flag=true）
                           └─ 校验发货单归属，提取 details
```

**以当前订单是否命中作为切换条件，不用固定的七天判断。** 当前订单已命中但普通详情为 `null` 或归属冲突时，不能仅把它当成“没找到订单”，绕开校验切到历史分支自动继续；应根据该业务的异常规则处理。

此顺序是单订单的**优先查询方案**，不是跨当前、历史两个数据区的全量归并。若目标是还原完整补发、重建单据和发货履约链路，应额外对两侧进行关联与去重，不可凭当前接口命中就认定历史区无相关记录。

### 8.5 历史详情为空时如何找回型号

历史订单可能出现：

```text
trade.history.get             → 返回 orders[].code
trade.detail.get              → orderDetail = null
trade.deliverys.history.get   → 返回 deliverys[].details[].item_code
```

2026-10-14 使用真实 API 对先前 22 笔历史型号缺失订单复测：**22/22 笔成功取得可信的非赠品型号**，其中 **21/22** 与已有型号登记完全一致；另一笔返回多个非赠品型号，原登记只写了其中一个。此结论是样本实测，不代表所有未发货或取消的历史订单都一定有发货明细。

### 8.6 多个 ERP 内部单号与归属校验

补发、人工补录或重新创建订单后，一个平台订单号可能有多个内部 `code`，甚至分布于当前和历史数据区。实测还存在某个内部单号查询到的发货单，其 `platform_code` 实际指向**另一笔订单**的情况。

定向查询需要遵守：

1. 检查 `total` 与实际收齐订单条数，未收全不能判定唯一归属。
2. 当历史订单返回多个内部 `code`，逐一确认相关单据都归属同一家可信店铺，不能盲用第一条。
3. 使用发货商品前核对完整 `deliverys[].platform_code`、`shop_code` 及内部 `code` 与目标订单一致；不一致的明细不得采用。
4. 从 `details[].item_code` 取商品代码，排除 `is_gift` 赠品，去除空值、去重；多个非赠品型号都应保留。

若业务系统采用“人工填写优先”的规则，API 查到的型号只用于补空白字段，不能因为接口结果更完整就直接覆盖人工已有值。这是应用层写入规则，并非 C-ERP API 自身的行为。

### 8.7 近期 / 历史订单归档边界实测

| 2026-10-14 测试样本 | `trade.get` | `trade.history.get` | 观察 |
| --- | --- | --- | --- |
| 10/12～10/14 的部分订单 | 有 | 无 | 近期订单不能只依赖历史接口 |
| 10/08～10/10 的部分订单 | 有 | 无 | 当前数据区仍可命中 |
| 10/05～10/06 的部分订单 | 有 | 有 | 两接口可重叠，内部单号不同 |
| 部分已归档订单 | 无 | 有 | 历史订单接口与历史发货接口可补查 |
| 10/07 的部分订单 | 有 | 无或有 | 不存在已证实的固定七天互斥切换点 |

注意：按时间窗口筛选出的 ERP 内部单据，可能是在后续日期创建或重建的，不能把筛选窗口直接等同于 `orders[].createtime`。上述结论限于真实测试租户，不宣称跨租户具有相同归档策略。公开文档不展示原始订单号、客人信息或真实密钥。

### 9.3 根据历史订单内部编号定向查询发货商品

当 `trade.get` 没找到、`trade.history.get` 已返回 `orders[].code` 时，直接定向查询该历史单据的发货明细，不需要遍历历史日期窗口：

```json
{
  "method": "gy.erp.trade.deliverys.history.get",
  "code": "<trade.history.get 返回的 orders[].code>",
  "detail_flag": true,
  "page_no": 1,
  "page_size": 100
}
```

以上仅为**业务参数**示例，实际调用仍需公共鉴权字段及 `sign`。存在多条历史 ERP 内部单号时应逐个查询，并检查 `total`、实际返回数量及分页完整性。

从 `deliverys[].details[].item_code` 提取商品型号之前，需要核对 `deliverys[].code`、完整 `platform_code` 及 `shop_code`。赠品由 `details[].is_gift` 识别。查询结果里如果没有归属可信的明细，应明确标记为型号暂不可得，不应使用别的订单的商品信息。

**适用边界**：本租户已实测可用历史订单内部 `orders[].code` 作为该发货查询接口的 `code` 参数；不能仅凭字段同名就保证所有租户、所有接口版本的内部订单编号和发货单编号恒等。其它租户须先验证。

## 10. 近期 / 历史发货单差异

这是当前最重要的接口边界。

| 能力 | `deliverys.get` | `deliverys.history.get` |
| --- | --- | --- |
| 数据区 | 近期 | 历史 |
| 修改时间查询 | 已验证支持 | 已验证不支持 |
| 发货时间查询 | 支持 | 必须使用 |
| `warehouse_code` 服务端筛选 | 已验证支持 | 已验证无效 / 不应依赖 |
| `detail_flag=true` | 已验证 | 已验证 |
| `del=0/1` | 已验证支持 | 已验证不能照搬 |
| 定向按 `code` | 可用 | 已验证可用 |
| 适合用途 | 持续增量、状态变化 | 历史回填 |

### 10.1 数据分层

真实租户定向验证结果：

```text
较老发货单
deliverys.get          → 0
deliverys.history.get  → 1

近期发货单
deliverys.get          → 1
deliverys.history.get  → 0
```

因此：

> `deliverys.get` 返回成功且 `total=0`，不能单独证明历史数据不存在。

### 10.2 归档边界与定向订单查询的区别

发货单实测与“约一周后进入历史区”的外部案例相符，但**没有验证出精确的 `7 × 24` 小时硬切点**。订单接口在 2026-10-14 的新增实测更显示：当前与历史订单记录可以重叠，且同一个平台订单号可能关联不同 ERP 内部单据。不要拿订单创建日期直接推断某一接口必然命中。

对于**批量发货数据同步**，仍建议近期与历史两个数据区分别采集、允许区间重叠，最终按发货单 `code` 和明细 `id` 幂等合并。

对于**按平台订单号定向查询型号**，推荐第 8.4 节的当前优先、未命中再查历史的顺序。这属于减少不必要查询的业务选择；若需完整收集跨区补发和履约信息，仍应覆盖两个数据区。



### 10.3 历史接口的仓库过滤

真实请求中，即使给历史接口额外传入 `warehouse_code`，仍会返回多个仓库。

因此历史数据应按：

```text
查询完整历史窗口
→ 客户端按 warehouse_code 过滤
→ 再进入后续业务处理
```

不能假设历史接口会服务端过滤仓库。

### 10.4 历史接口不能使用修改时间做增量

仅向历史接口传：

```text
start_modify_date
end_modify_date
```

真实响应：

```text
PARAM ERR 发货开始时间必填
```

同时传发货时间和修改时间时，也没有观察到修改时间筛选效果。

结论：

```text
deliverys.history.get
→ 以 start_delivery_date / end_delivery_date 为查询时间
→ 不承担近期接口的“按修改时间捕获后续状态变化”职责
```

### 10.5 历史接口的作废状态

`deliverys.get` 已验证支持：

```text
del = 0
del = 1
```

`deliverys.history.get` 的已查资料中没有对应 `del` 参数。真实请求追加 `del=1` 后，也没有观察到筛选效果。

当前结论：

- 不应把近期接口的正常单 / 作废单双流查询直接复制到 history。
- 历史单归档后再次发生取消或作废时，最终补偿机制仍属于 **待验证项**。

<div class="cerp-doc-flow" role="group" aria-label="C-ERP 数据采集职责">
  <section>
    <b>近期增量</b>
    <code>gy.erp.trade.deliverys.get</code>

接口职责应保持分离：

- 近期接口负责持续捕获修改、取消和作废。
- 历史接口负责已归档发货事实。
- 历史查询后由客户端执行仓库过滤。
- 重叠区间通过业务主键幂等去重，而不是依赖精确归档时间点。

## 16. 当前待验证项

目前仍不应下结论的部分：

- 历史发货单归档后的取消 / 作废如何被稳定重新发现。
- 近期 / 历史**订单及发货数据区**的精确切换时刻是否固定（七天不是已经验证的硬边界）。
- 同一平台订单号跨当前与历史订单接口出现多条 ERP 内部单据时，完整履约与补发合并的业务边界。
- 将历史订单内部 `orders[].code` 用于 `deliverys.history.get` 定向查询在其它租户或不同接口版本中的适用范围。
- 未列出的接口参数和返回字段在不同租户、版本中的兼容性。

这些边界在真实调用确认前，应保持“待验证”，不要从第三方资料直接写成固定业务规则。
