这个博客没有常驻后端进程。它先由 Astro 把源码构建成静态文件，再由 GitHub Actions 把构建产物发布到 GitHub Pages；读者访问时，Pages 直接返回已经生成好的 HTML、CSS、JavaScript 和图片。

<div class="pages-manual pages-opening" role="group" aria-label="这个博客部署方式的一句话结论">
  <div class="pages-opening__label">DEPLOYMENT MODEL</div>
  <strong>源码不是网站，<span>dist 产物</span>才是 Pages 最终托管的内容。</strong>
  <p>Astro 负责“生成”，GitHub Actions 负责“自动执行”，GitHub Pages 负责“公开托管”。</p>
  <div class="pages-opening__roles">
    <span><b>Astro</b> 构建器</span>
    <span><b>Actions</b> 自动化</span>
    <span><b>Pages</b> 静态托管</span>
  </div>
</div>

## 浏览器访问时，真正发生了什么

<div class="pages-manual pages-board" role="group" aria-label="浏览器访问 GitHub Pages 静态站点的完整请求链路">
  <header class="pages-board__header">
    <div>
      <span class="pages-kicker">01 · REQUEST PATH</span>
      <strong>一次访问，只是在请求已经发布好的静态文件</strong>
    </div>
    <span class="pages-status pages-status--green">运行时无构建</span>
  </header>

  <div class="pages-definition">
    <b>GitHub Pages</b>
    <span>GitHub 提供的静态站点托管服务，可以从仓库内容或 Actions 产物发布 HTML、CSS 和 JavaScript 网站。</span>
    <a href="https://docs.github.com/en/pages/getting-started-with-github-pages/what-is-github-pages">GitHub 官方定义</a>
  </div>

  <div class="pages-track" aria-label="从浏览器到页面资源的访问链路">
    <article class="pages-node pages-node--browser">
      <small>REQUEST</small>
      <strong>浏览器请求 URL</strong>
      <code>https://apexcheng.github.io/</code>
      <p>首页或文章地址成为一条 HTTPS 请求。</p>
    </article>
    <i aria-hidden="true">→</i>
    <article class="pages-node pages-node--host">
      <small>HOST</small>
      <strong>GitHub Pages 接收</strong>
      <code>apexcheng.github.io</code>
      <p>Pages 按已经发布的站点版本查找对应文件。</p>
    </article>
    <i aria-hidden="true">→</i>
    <article class="pages-node pages-node--asset">
      <small>RESPONSE</small>
      <strong>返回静态资源</strong>
      <code>HTML · CSS · JS · images</code>
      <p>浏览器下载资源并在本地完成页面呈现。</p>
    </article>
  </div>

  <div class="pages-runtime-map">
    <div class="pages-runtime-map__present">
      <span>访问时存在</span>
      <div>
        <b>静态文件</b>
        <b>浏览器渲染</b>
        <b>Pages 托管</b>
      </div>
    </div>
    <div class="pages-runtime-map__absent">
      <span>这个项目访问时不需要</span>
      <div>
        <s>Node 常驻进程</s>
        <s>应用数据库</s>
        <s>Nginx 自建服务器</s>
        <s>每次请求现场构建</s>
      </div>
    </div>
  </div>

  <div class="pages-evidence">
    <span>本站证据</span>
    <p><code>astro.config.mjs</code> 没有服务端 adapter；当前部署链路以 Astro 静态构建和 Pages artifact 为核心。</p>
    <b>边界：需要登录、数据库写入或实时服务端计算时，静态 Pages 本身不能替代后端。</b>
  </div>
</div>

GitHub Pages 有用户 / 组织站点和项目站点两类。用户站点仓库使用特殊名称 <code>&lt;owner&gt;.github.io</code>，默认地址位于域名根路径；项目站点默认位于 <code>/&lt;repository&gt;/</code> 子路径。这个差异会直接影响 Astro 的 `base`。

## Astro 怎样把文章变成可部署文件

<div class="pages-manual pages-board" role="group" aria-label="Astro 从源码构建到 dist 静态产物的完整变换">
  <header class="pages-board__header">
    <div>
      <span class="pages-kicker">02 · BUILD TRANSFORMATION</span>
      <strong>构建把“项目结构”翻译成“浏览器能直接读取的文件”</strong>
    </div>
    <span class="pages-status pages-status--blue">npm run build</span>
  </header>

  <div class="pages-input-output">
    <div class="pages-input-output__side">
      <span>SOURCE · 输入</span>
      <strong>仓库里的开发文件</strong>
      <ul>
        <li><code>src/content/posts/</code>：Markdown / MDX 文章</li>
        <li><code>src/pages/</code>：页面与静态路由</li>
        <li><code>src/components/</code>：Astro 组件</li>
        <li><code>src/styles/</code>：站点样式</li>
      </ul>
    </div>
    <div class="pages-compiler">
      <span>ASTRO BUILD</span>
      <b>读取内容</b>
      <i aria-hidden="true">↓</i>
      <b>生成路由</b>
      <i aria-hidden="true">↓</i>
      <b>编译与打包</b>
      <i aria-hidden="true">↓</i>
      <strong>写入 dist/</strong>
    </div>
    <div class="pages-input-output__side pages-input-output__side--output">
      <span>ARTIFACT · 输出</span>
      <strong>可公开托管的静态站点</strong>
      <ul>
        <li><code>index.html</code>：入口页面</li>
        <li><code>articles/.../index.html</code>：文章页</li>
        <li><code>_astro/...</code>：编译后的 CSS / JS</li>
        <li>图片、字体、RSS 等公开资源</li>
      </ul>
    </div>
  </div>

  <div class="pages-project-proof">
    <article>
      <span>构建命令</span>
      <code>npm run build</code>
      <p><code>package.json</code> 当前映射为 <code>astro build</code>。</p>
    </article>
    <article>
      <span>默认输出</span>
      <code>dist/</code>
      <p>项目没有覆盖 <code>outDir</code>，沿用 Astro 默认静态输出目录。</p>
    </article>
    <article>
      <span>发布原则</span>
      <code>不提交 dist</code>
      <p>远端 Action 会基于同一提交重新安装、构建并上传产物。</p>
    </article>
  </div>

  <div class="pages-verdict">
    <span>这一章的判断</span>
    <strong>本地源码能打开，不等于部署产物能生成；`npm run build` 才是发布前最接近云端的一次检查。</strong>
  </div>
</div>

可复制的本地构建命令：

```bash
npm run build
npm run preview
```

`preview` 用于检查刚生成的静态产物，不是生产服务器。Astro 官方部署文档也将默认构建命令写为 `npm run build`、默认发布目录写为 `dist`，可参考 [Astro 部署说明](https://docs.astro.build/en/guides/deploy/)。

## GitHub Actions 怎样完成自动发布

<div class="pages-manual pages-board" role="group" aria-label="GitHub Actions build 和 deploy 两个任务的发布泳道">
  <header class="pages-board__header">
    <div>
      <span class="pages-kicker">03 · DELIVERY PIPELINE</span>
      <strong>main 分支只触发流程，真正交付的是 build job 产出的 artifact</strong>
    </div>
    <span class="pages-status pages-status--violet">2 jobs</span>
  </header>

  <div class="pages-trigger-strip">
    <div>
      <span>AUTO</span>
      <strong>push → main</strong>
      <p>main 收到新提交时自动触发。</p>
    </div>
    <div>
      <span>MANUAL</span>
      <strong>workflow_dispatch</strong>
      <p>允许从 Actions 页面手动运行。</p>
    </div>
    <div>
      <span>QUEUE</span>
      <strong>group: pages</strong>
      <p><code>cancel-in-progress: false</code>，进行中的发布不被新运行取消。</p>
    </div>
  </div>

  <div class="pages-swimlane">
    <div class="pages-swimlane__label">
      <span>BUILD JOB</span>
      <small>输入：仓库提交</small>
    </div>
    <div class="pages-swimlane__steps">
      <article>
        <b>1</b>
        <strong>Checkout</strong>
        <code>actions/checkout@v6</code>
        <p>把触发这次运行的仓库内容检出到 runner。</p>
      </article>
      <i aria-hidden="true">→</i>
      <article>
        <b>2</b>
        <strong>Install + Build</strong>
        <code>withastro/action@v6</code>
        <p>使用 npm 安装依赖、执行 Astro 构建并准备 Pages artifact。</p>
      </article>
      <i aria-hidden="true">→</i>
      <article class="pages-swimlane__artifact">
        <b>3</b>
        <strong>Pages artifact</strong>
        <code>静态构建产物</code>
        <p>这是 build job 交给 deploy job 的发布对象。</p>
      </article>
    </div>
  </div>

  <div class="pages-job-gate">
    <span>needs: build</span>
    <b>只有 build 成功，deploy 才能开始</b>
  </div>

  <div class="pages-swimlane pages-swimlane--deploy">
    <div class="pages-swimlane__label">
      <span>DEPLOY JOB</span>
      <small>输入：Pages artifact</small>
    </div>
    <div class="pages-swimlane__steps pages-swimlane__steps--deploy">
      <article>
        <b>4</b>
        <strong>Deploy Pages</strong>
        <code>actions/deploy-pages@v5</code>
        <p>把上一任务的 artifact 发布到 <code>github-pages</code> environment。</p>
      </article>
      <i aria-hidden="true">→</i>
      <article class="pages-swimlane__online">
        <b>5</b>
        <strong>站点版本更新</strong>
        <code>https://apexcheng.github.io/</code>
        <p>成功运行会输出部署 URL；外部是否已更新仍需线上验收。</p>
      </article>
    </div>
  </div>

  <div class="pages-permissions">
    <span>最小权限与发布身份</span>
    <div>
      <code>contents: read</code>
      <code>pages: write</code>
      <code>id-token: write</code>
    </div>
    <p>分别用于读取仓库、写入 Pages 部署和使用 OIDC 身份令牌；这些字段与当前 workflow 一致。</p>
  </div>

  <div class="pages-verdict">
    <span>这一章的判断</span>
    <strong>构建失败时不会进入发布；发布成功也只证明 artifact 已部署，页面内容与缓存仍要单独验收。</strong>
  </div>
</div>

当前仓库的真实 workflow 是 `.github/workflows/deploy.yml`。它与 [Astro 官方 GitHub Pages 指南](https://docs.astro.build/en/guides/deploy/github/) 的两任务结构一致；GitHub 也把 “checkout → build → upload artifact → deploy-pages” 作为自定义 Actions 发布的标准链路，见 [GitHub Pages 发布源说明](https://docs.github.com/en/pages/getting-started-with-github-pages/configuring-a-publishing-source-for-your-github-pages-site)。

## site、base 和仓库名怎样共同决定地址

<div class="pages-manual pages-board" role="group" aria-label="GitHub Pages 用户站点和项目站点的地址映射">
  <header class="pages-board__header">
    <div>
      <span class="pages-kicker">04 · ADDRESS MODEL</span>
      <strong>先判断仓库属于哪种 Pages 站点，再决定 Astro 是否需要 base</strong>
    </div>
    <span class="pages-status pages-status--amber">路径最易出错</span>
  </header>

  <div class="pages-address-compare">
    <article class="pages-address-card pages-address-card--current">
      <span>USER SITE · 当前博客</span>
      <strong>仓库名匹配特殊规则</strong>
      <code>apexcheng.github.io</code>
      <div class="pages-address-card__mapping">
        <small>默认站点地址</small>
        <b>https://apexcheng.github.io/</b>
      </div>
      <ul>
        <li><code>site</code>：设置完整域名</li>
        <li><code>base</code>：当前不配置</li>
        <li>页面和资源从根路径 <code>/</code> 开始</li>
      </ul>
    </article>

    <article class="pages-address-card">
      <span>PROJECT SITE · 对照情况</span>
      <strong>普通仓库作为项目站点</strong>
      <code>about</code>
      <div class="pages-address-card__mapping">
        <small>默认站点地址</small>
        <b>https://apexcheng.github.io/about/</b>
      </div>
      <ul>
        <li><code>site</code>：仍是所属域名</li>
        <li><code>base</code>：通常配置为 <code>/about</code></li>
        <li>内部链接必须带上项目子路径</li>
      </ul>
    </article>
  </div>

  <div class="pages-config-proof">
    <div>
      <span>当前 astro.config.mjs</span>
      <pre><code>{`export default defineConfig({
  site: 'https://apexcheng.github.io',
  devToolbar: {
    enabled: true,
  },
  integrations: [mdx()],
});`}</code></pre>
    </div>
    <aside>
      <span>读配置的顺序</span>
      <ol>
        <li>域名来自 <code>site</code>。</li>
        <li>未设置 <code>base</code>，因此构建根路径是 <code>/</code>。</li>
        <li><code>withBase()</code> 用 <code>import.meta.env.BASE_URL</code> 统一生成内部链接。</li>
      </ol>
    </aside>
  </div>

  <div class="pages-path-failure">
    <div>
      <span>错误配置示例</span>
      <code>base: '/blog'</code>
    </div>
    <i aria-hidden="true">→</i>
    <div>
      <span>构建出的资源路径</span>
      <code>/blog/_astro/...</code>
    </div>
    <i aria-hidden="true">→</i>
    <div class="pages-path-failure__result">
      <span>部署在根站点时</span>
      <strong>CSS / JS 可能 404</strong>
    </div>
  </div>

  <div class="pages-evidence">
    <span>边界与结论</span>
    <p>仓库改名、改为项目站点或接入自定义域名时，都要重新核对 `site`、`base`、Pages 设置和内部链接；不能只改其中一个。</p>
    <b>当前“根路径部署”由本地配置和仓库命名共同支持；GitHub 仓库的 Pages Source 仍需在 Settings 中运行验证。</b>
  </div>
</div>

Astro 官方说明明确指出：项目站点通常要把仓库名配置为 `base`，而当仓库名符合 `<username>.github.io` 时可以跳过。当前项目的 `src/utils/paths.ts` 还保留了 `withBase()`，因此内部地址不会把根路径写死。

## 从改文章到线上验收，应该按哪条操作链

<div class="pages-manual pages-board" role="group" aria-label="从本地修改到线上验收的发布操作链">
  <header class="pages-board__header">
    <div>
      <span class="pages-kicker">05 · OPERATOR RUNBOOK</span>
      <strong>发布不是 push 结束，而是本地、Actions、线上三次验收</strong>
    </div>
    <span class="pages-status pages-status--blue">可复制执行</span>
  </header>

  <div class="pages-runbook">
    <article>
      <div class="pages-runbook__number">01</div>
      <div>
        <span>CONTENT</span>
        <strong>修改文章或代码</strong>
        <p>正式文章位于 <code>src/content/posts/</code>；公开文章保持 <code>draft: false</code> 和 <code>private: false</code>。</p>
      </div>
      <b>产出：源码变更</b>
    </article>
    <article>
      <div class="pages-runbook__number">02</div>
      <div>
        <span>LOCAL GATE</span>
        <strong>先测试，再构建</strong>
        <pre><code>{`npm test
npm run build`}</code></pre>
        <p>测试负责已有规则，构建负责 MDX、路由和静态生成。</p>
      </div>
      <b>产出：可生成的 dist</b>
    </article>
    <article>
      <div class="pages-runbook__number">03</div>
      <div>
        <span>VERSION</span>
        <strong>只提交本次相关文件</strong>
        <pre><code>{`git add src/content/posts/my-new-article.mdx
git commit -m "更新文章"`}</code></pre>
        <p>提交记录定义这次远端构建使用的源码版本。</p>
      </div>
      <b>产出：Git commit</b>
    </article>
    <article>
      <div class="pages-runbook__number">04</div>
      <div>
        <span>TRIGGER</span>
        <strong>推送 main</strong>
        <pre><code>{`git push origin main`}</code></pre>
        <p>当前 workflow 监听 main；其他分支不会通过这条 push 规则自动部署。</p>
      </div>
      <b>产出：Actions run</b>
    </article>
    <article>
      <div class="pages-runbook__number">05</div>
      <div>
        <span>REMOTE GATE</span>
        <strong>检查 build 与 deploy</strong>
        <p>先确认 build job，再确认 deploy job；绿色状态来自真实运行，不从 YAML 推断。</p>
      </div>
      <b>产出：deployment URL</b>
    </article>
    <article>
      <div class="pages-runbook__number">06</div>
      <div>
        <span>BROWSER GATE</span>
        <strong>检查真实页面</strong>
        <p>至少打开首页、目标文章和一个静态资源；必要时使用无痕窗口排除缓存。</p>
      </div>
      <b>产出：线上验收</b>
    </article>
  </div>

  <div class="pages-release-gates">
    <article>
      <span>GATE A</span>
      <strong>本地构建通过</strong>
      <p>证明这份源码能生成静态站点。</p>
    </article>
    <article>
      <span>GATE B</span>
      <strong>Actions 两个 job 通过</strong>
      <p>证明远端环境完成构建与部署。</p>
    </article>
    <article>
      <span>GATE C</span>
      <strong>浏览器访问正确</strong>
      <p>证明路径、资源与内容对读者可用。</p>
    </article>
  </div>

  <div class="pages-verdict">
    <span>这一章的判断</span>
    <strong>三个闸门不能互相替代：本地成功不代表远端权限正确，Actions 成功也不代表浏览器没有缓存或路径问题。</strong>
  </div>
</div>

本文没有把 `dist/` 加入提交命令，因为当前部署方式会在 GitHub runner 上重新构建。若将来改为分支目录发布，交付对象与操作链也必须随之调整。

## 部署失败时，怎样分层定位

<div class="pages-manual pages-board pages-diagnostic" role="group" aria-label="GitHub Pages 部署五层故障诊断图">
  <header class="pages-board__header">
    <div>
      <span class="pages-kicker">06 · LAYERED DIAGNOSIS</span>
      <strong>不要从“页面不对”直接猜原因，先找到故障发生在哪一层</strong>
    </div>
    <span class="pages-status pages-status--red">5 层定位</span>
  </header>

  <div class="pages-diagnostic__legend">
    <span><i class="is-red"></i> 当前故障层</span>
    <span><i class="is-green"></i> 已通过证据</span>
    <span><i class="is-gray"></i> 尚未检查</span>
  </div>

  <div class="pages-diagnostic__stack">
    <article>
      <div class="pages-diagnostic__level">L1</div>
      <div>
        <span>SOURCE</span>
        <strong>源码与内容层</strong>
        <p>MDX 语法、frontmatter、import、公开状态、文件名是否正确。</p>
      </div>
      <div class="pages-diagnostic__check">
        <b>证据</b>
        <code>npm test</code>
        <code>目标文件 diff</code>
      </div>
      <div class="pages-diagnostic__signal">构建前错误</div>
    </article>

    <article>
      <div class="pages-diagnostic__level">L2</div>
      <div>
        <span>BUILD</span>
        <strong>Astro 构建层</strong>
        <p>依赖是否可安装，路由和 MDX 是否能生成，<code>dist/</code> 是否完整。</p>
      </div>
      <div class="pages-diagnostic__check">
        <b>证据</b>
        <code>npm run build</code>
