很多人在长期使用 AI 助手后，都会遇到同一个问题：

> 昨天已经告诉它的事情，今天为什么又要重新解释？

一次性聊天只需要当前上下文；但维护博客、开发 Agent、管理自动化流程时，项目背景、历史决策、长期偏好和踩坑经验都需要持续保留。

所以我把 GBrain 接进了自己的 OpenClaw。目标不是多装一个搜索工具，而是让 Agent 形成两条真正可运行的闭环：

- **自动想起来**：每次对话开始时，主动召回相关长期知识。
- **自动记下来**：新消息进入后，判断哪些内容值得长期保存，并写回知识库。

## 先看整体：它不是一个插件，而是一套双闭环系统

GBrain 不是另一个聊天机器人，也不是 OpenClaw 的替代品。

OpenClaw 负责理解目标、推理、调用工具和执行任务；GBrain 负责保存长期项目、历史决定、人物关系和可复用经验。两者之间还需要 Context Engine、Retrieval Reflex、MCP 和 Signal Detector 把读写链路连接起来。

## 为什么只安装 MCP 还不够？

我最开始也以为，安装 GBrain MCP，让 Agent 能搜索和写入知识，就已经完成接入。

实际只完成了最下面一层：**Agent 可以主动使用工具**。如果每次都要靠模型临时判断“现在是不是应该搜索 GBrain”，记忆仍然不稳定。

### 第一步：安装 GBrain，先确认 CLI 正常

GBrain 官方更推荐让 Agent 读取安装说明并执行。可以把下面这段直接交给能够访问网络和终端的 Agent：

```text
Retrieve and follow the instructions at:
https://raw.githubusercontent.com/garrytan/gbrain/master/INSTALL_FOR_AGENTS.md
```

只安装 CLI 时，可以使用：

```bash
bun install -g github:garrytan/gbrain
gbrain doctor
```

这篇文章不是官方安装文档的复述。官方说明负责把 GBrain 装起来；这里重点记录它怎样进入现有 OpenClaw，并形成自动召回、自动写入和多会话稳定运行。

### 第二步：多会话场景直接使用 PostgreSQL 17

我最初使用 PGLite。单独运行 GBrain 没问题，但 OpenClaw 的 MCP runtime 会按 session 启动独立进程，多个 `gbrain serve` 可能同时争用一份数据库文件。

<div class="brain-poster brain-lock" role="group" aria-label="PGLite 多会话锁冲突与 PostgreSQL 解决方案">
  <header class="brain-panel-title">
    <span>STORAGE DECISION</span>
    <strong>问题不是 GBrain 慢，而是多个会话在抢同一把文件锁</strong>
  </header>
  <div class="brain-lock__flow">
    <section><b>会话 1</b><span>gbrain serve</span><strong>持有 PGLite 锁</strong></section>
    <section><b>会话 2</b><span>gbrain serve</span><strong>等待锁</strong></section>
    <section><b>会话 3</b><span>gbrain serve</span><strong>继续等待</strong></section>
    <i>→</i>
    <section class="is-error"><b>最终表现</b><span>MCP 启动</span><strong>卡住约 30 秒</strong></section>
  </div>
  <div class="brain-lock__solution">
    <span>最终方案</span>
    <strong>PostgreSQL 17 + pgvector</strong>
    <p>把共享状态交给数据库服务，不再让多个 session 争用同一个本地文件。</p>
  </div>
</div>

```bash
brew install postgresql@17 pgvector
brew services start postgresql@17

createdb gbrain
psql gbrain -c 'CREATE EXTENSION IF NOT EXISTS vector;'

gbrain init \
  --url "postgresql://<user>@127.0.0.1:5432/gbrain" \
  --no-embedding
```

我当前没有配置 Embedding，所以使用 `--no-embedding`。这不会影响关键词搜索、实体召回、MCP 查询和 Signal Detector 写入，只是暂时没有完整的向量语义检索。

我实际安装时还遇到一次版本兼容：当时 Homebrew 的 pgvector 扩展没有落到 PostgreSQL 16 的扩展目录，换成 PostgreSQL 17 后恢复正常。最终只保留一个数据库版本，避免两套服务同时占端口。

### 第三步：建立独立的 Brain Repo

长期知识没有直接塞进 OpenClaw workspace，而是单独保存在：

```text
~/brain
```

```bash
mkdir -p ~/brain
cd ~/brain
git init

gbrain sources add brain --path ~/brain
gbrain sync --source brain --no-pull --no-embed
```

我最终只保留一个明确的长期 source：`brain`。后面的 MCP 写入也必须明确落到这个 source。

### 第四步：接入 Retrieval Reflex 和 MCP

Retrieval Reflex 负责识别相关实体，MCP 负责让 Agent 主动搜索和写入。

```bash
gbrain integrations install retrieval-reflex \
  --target ~/.openclaw/workspace

openclaw mcp add gbrain \
  --command "$(command -v gbrain)" \
  --arg serve \
  --cwd ~/brain \
  --env GBRAIN_SOURCE=brain
```

MCP 配置中最容易被忽略的不是 `cwd`，而是：

```text
GBRAIN_SOURCE=brain
```

`cwd=~/brain` 不会自动保证所有写入都路由到 `brain`。没有明确 source 时，写入可能回退到 `default`。

```json
{
  "command": "/Users/<user>/.bun/bin/gbrain",
  "args": ["serve"],
  "cwd": "/Users/<user>/brain",
  "env": {
    "GBRAIN_SOURCE": "brain"
  }
}
```

最后运行：

```bash
openclaw mcp doctor
```

我当时的真实结果是 `gbrain: ok`。

### 第五步：让 GBrain 真正成为 Context Engine

如果 OpenClaw 仍然使用 `contextEngine = legacy`，GBrain 只是一个可选工具，没有进入每轮上下文组装。

我最终使用的 slot 是：

```json
{
  "plugins": {
    "slots": {
      "memory": "memory-core",
      "contextEngine": "gbrain-context"
    }
  }
}
```

<div class="brain-poster brain-id-check" role="group" aria-label="GBrain 插件 ID 与 Context Engine ID 的区别">
  <div class="is-wrong"><span>插件 ID</span><strong>gbrain-context-engine</strong><small>插件叫什么</small></div>
  <i>≠</i>
  <div class="is-right"><span>Context Engine ID</span><strong>gbrain-context</strong><small>slot 应该填写的值</small></div>
</div>

我的本地桥接插件位于 `~/.openclaw/extensions/gbrain-context-engine`，只负责三件事：

1. 加载 GBrain 官方 Context Engine；
2. 适配当前版本 OpenClaw 与 GBrain 的 `prompt` / `messages` 参数差异；
3. 在 `message_received` 上启动官方 Signal Detector。

这不是所有版本都要长期保留的代码。升级 OpenClaw 或 GBrain 后，应先检查上游是否已经原生解决，能删除桥接层就删除。

### 第六步：让 Signal Detector 通过系统事件自动运行

`signal-detector/SKILL.md` 里的 `triggers:` 只是 Skill 描述，不是 OpenClaw 的原生事件机制。在 `AGENTS.md` 中写“每条消息都启动 Signal Detector”也只是 Prompt 约束，不够稳定。

我最终使用宿主侧 `message_received` hook，在每条入站消息后启动隐藏子 Agent：

```js
api.on('message_received', (event, ctx) => {
  void runSignalDetector(event.content ?? '', ctx)
    .catch((error) => api.logger.error(String(error)));
});
```

这里最重要的是 `void`：后台记忆任务继续运行，主 Agent 不等待它完成。

<div class="brain-poster brain-timing" role="group" aria-label="主 Agent 回复与 Signal Detector 后台写入时序">
  <div><span>用户消息</span><strong>进入 OpenClaw</strong></div>
  <i>→</i>
  <div class="is-fast"><span>主 Agent</span><strong>约 3 秒回复</strong><small>不等待记忆任务</small></div>
  <i>∥</i>
  <div class="is-background"><span>Signal Detector</span><strong>约 6.5 秒完成</strong><small>后台写入 source_id = brain</small></div>

这才算自动记忆闭环真正成立。

## 出了问题，不要把所有故障都叫做“没生效”

很多现象看起来都像 GBrain 没有工作，但可能分别发生在 source、同步、检索、MCP、Context Engine 或 Signal Detector。正确排查方式不是反复重启，而是逐层拿证据。

<div class="brain-poster brain-diagnostics" role="group" aria-label="GBrain 与 OpenClaw 分层故障诊断图">
  <header class="brain-poster__title">
    <div>
      <span>CHAPTER 05 · DIAGNOSTICS</span>
      <strong>每层先证明正常，再进入上一层</strong>

  </header>

  <ol class="brain-diagnostics__ladder">
    <li><b>01</b><div><span>source 与同步</span><code>gbrain status</code></div><strong>证据：目标 source 存在，最近同步有记录</strong></li>
    <li><b>02</b><div><span>页面与检索</span><code>gbrain search "确定存在的关键词" --limit 3</code></div><strong>证据：目标页面真实返回</strong></li>
    <li><b>03</b><div><span>数据库与质量</span><code>gbrain doctor --fast</code></div><strong>证据：核心存储和检索检查正常</strong></li>
    <li><b>04</b><div><span>MCP 传输</span><code>openclaw mcp doctor gbrain --probe</code></div><strong>证据：服务启动并完成握手</strong></li>
    <li><b>05</b><div><span>插件与 slot</span><code>slot = gbrain-context</code></div><strong>证据：插件 loaded，Context Engine 正确</strong></li>
    <li class="is-final"><b>06</b><div><span>自动召回行为</span><code>新会话 + 独特事实</code></div><strong>证据：回答与日志都证明注入发生</strong></li>
  </ol>

  <div class="brain-pit-grid">
    <section>
      <span>装了 MCP，但新会话不自动想起</span>
      <strong>只完成了主动工具层</strong>
      <p>检查 Context Engine 是否切到 <code>gbrain-context</code>。</p>
    </section>
    <section>
      <span>插件正常，slot 仍然不生效</span>

    </section>
    <section>
      <span>Context Engine loaded，但没有注入</span>
      <strong>prompt / messages 参数差异</strong>

    </section>

      <p>多 session 场景改用 PostgreSQL 17。</p>
    </section>
    <section>

      <strong>triggers 不是系统事件</strong>
      <p>使用宿主侧 <code>message_received</code> hook。</p>
    </section>
    <section>

## 最终验收：不要只看插件是否 loaded

配置完成后，我不会只看进程是否启动，而是按两条闭环做真实验收。

基础健康检查可以先运行：

```bash
openclaw health
openclaw mcp doctor
gbrain status
```

我当时的本机状态是：

```text
GBrain 0.42.57.0
brain source: pages=1
Embedding: 0%
Autopilot: not running
MCP: gbrain ok
```

但这些只说明服务状态，真正重要的是行为。

<div class="brain-poster brain-final-check" role="group" aria-label="GBrain 接入 OpenClaw 的最终验收清单">
  <header class="brain-poster__title">
