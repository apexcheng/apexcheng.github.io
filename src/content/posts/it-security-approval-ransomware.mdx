一家公司的 IT 水平到底怎么样？

以前我觉得，要看网络架构、服务器配置、安全体系、技术团队。

后来我发现，有时候根本不用这么复杂。只需要问几个问题：

- 知道 API 是什么吗？
- 知道钉钉机器人、应用所有权和 API 权限是什么关系吗？
- 知道 Windows 文件服务器为什么不应该让全公司共用一套登录凭据吗？
- 公司遭遇勒索软件之后，关键业务有没有经过验证的备用方案？

如果这些问题都说不清楚，却还负责全公司的信息化建设和安全审批，那事情就很有意思了。

更有意思的是：当这样的企业遇到勒索软件事故时，**生产线继续运转、其他部门基本正常工作，财务账务系统却过了约半个月还没恢复，连正常工资发放流程都受到影响。**

我没有拿到完整的安全取证报告，不知道最终入侵点、数据损失规模，也不知道每一位技术人员在后台做了什么。这篇文章不是事故责任认定，而是把我亲身经历的几次沟通和看见的业务后果摆在一起，看看所谓的“安全管理”，到底有没有讲道理。

<HighlightBox eyebrow="这篇文章最想吐槽的事" title="审批权限很严格，不等于信息安全做得好">
  技术风险需要具体分析：谁能访问什么、通过什么接口、什么身份、在什么条件下产生影响。如果连这些都没搞清楚，却能一句“有风险”否决方案，那不是专业审查，而是把未知当成了禁令。
</HighlightBox>

## 01｜勒索软件来了，半个月过去，财务业务还没恢复

某天凌晨，公司发生了一起大范围网络安全事件。

最初的内部消息称，ERP、MES、SRM、文件共享服务器、远程应用服务和超融合等受到影响，多台内网电脑也可能卷入其中。

请注意，我在这里特意使用“内部消息称”。

因为**系统访问不了、被主动隔离、虚拟机无法启动、共享文件被加密、服务器操作系统真正感染**，是完全不同的事情。没有技术取证和资产清单，不能因为一句“所有服务器中毒”就把这些混为一谈。

我们部门使用的是外部云端电商 ERP。公司所说的“ERP 服务器”，是否指其他部门的本地 ERP、集成服务或底层环境，我也不能确认。

但有几件事可以确认：

| 业务现场 | 我的观察 |
| --- | --- |
| 生产线 | 一直没有停产 |
| 其他部门日常工作 | 基本正常 |
| 财务账务与发薪 | 约半个月后，仍未恢复正常处理能力 |
| 具体服务器感染范围、备份状态 | 没有掌握可靠的核查结果 |

这说明公司不是全面停摆，但至少一项重要业务长时间受到影响。

有人会说：“勒索软件很复杂，半个月修不好，不奇怪。”

这句话有一半是对的。

如果备份被破坏，数据库损坏，域控失陷，超融合底层需要重建，经验丰富的团队同样可能修上几周甚至几个月。

可另一半问题是：

**企业 IT 的专业性，不能只看有没有能力把服务器修回来，还要看服务器一时修不回来，业务有没有别的路可走。**

工资发放不应该永远只剩“等系统修好”这一条路。只要工资数据可安全核实、审批链路与银行渠道可靠，企业就应该评估合规的备用流程。能不能实施，当然还取决于财务、管理层和实际数据状态。

所以，半个月还没恢复，不能单凭天数证明是哪位工程师技术差；但**半个月仍影响正常发薪，足以说明企业整体业务连续性保障的实际结果不理想**。

服务器灾备、数据备份、替代流程、业务优先级，哪一环有缺口，都值得查明。

CISA 的 [StopRansomware Guide](https://www.cisa.gov/stopransomware/ransomware-guide) 强调离线备份、定期恢复测试、清洁环境恢复，以及根据关键业务确定恢复顺序。

这些不是安全领域的“炫技”，而是企业真正出事时用来兜底的基础工作。

## 02｜申请一个钉钉机器人，仿佛在申请核武器发射权限

说回我亲自经历的技术沟通。

我们部门想把钉钉 AI 表格、开放平台 API 和机器人用在日常工作里。

需求一点也不玄乎：

- 用 API 自动写入业务数据，减少人工录入；
- 用 AI 字段分析商品链接、用户评价；
- 用仪表盘呈现分析结果；
- 在群聊中 @ 相应负责人处理订单、店铺消息；
- 有些事情通过机器人私聊通知指定人员。

这是一个数据处理和业务协作的自动化方案，不是为了“聊天好玩”才申请机器人。

但是，信息部的担忧集中在：机器人会不会读取全公司员工信息、钉盘文件和所有 AI 表格？

安全担忧完全可以有。问题是既然担忧，就应该把权限机制搞明白。

于是我详细解释过：

开放平台获得某类接口的使用许可，不等于自动拥有无限的数据访问权限；具体需要看应用申请的权限点、调用身份、接口类型，以及资源本身的访问规则。

以用户委托访问为例，需要应用得到授权，**同时这个用户本身有权访问该资源**，才能代表用户操作相应资源。

这套解释并不是我拍脑袋想出来的。钉钉的[权限概述](https://opensource.dingtalk.com/developerpedia/docs/learn/permission/intro/overview/)就明确区分了“委托权限”和“应用权限”。

当然，应用级访问可能具有比用户委托更宽的范围。不能把“只允许我们部门使用应用”直接等同于“应用绝对只能读取部门数据”。

也正因为如此，专业评审应该检查**具体权限点和实际 API 调用方式**，而不是看到“钉盘权限”四个字就认定应用能删除全公司文件。

结果，我得到的回应，重点竟然是：

> 1、AI 表格类似于 EXCEL 表格，机器人群聊/私聊表现并不突出。  
> 2、会存在信息泄露和丢失的风险。  
> 3、随着数据量的增长，涉及钉钉费用高。  
> 没有清晰的需求目标、应用功能、费用分析，不赞成开通这些权限。

看到第一条，我是真的有点绷不住。

### “AI 表格类似 Excel”，所以呢？

我申请的是 API 数据读写，是自动分析，是群聊任务通知。

你回复的是“AI 表格类似 Excel”“机器人群聊私聊表现不突出”。

这就像我想申请数据库服务器存储数据，对方评价说：

“数据库跟 Excel 差不多，而且它聊天也不怎么智能。”

**需求涉及什么技术能力都没对齐，就已经开始否定功能价值。**

不是每一个叫“机器人”的东西，主要价值都是陪人聊天。

有的机器人最重要的工作，是在正确的时间把正确的信息送给正确的人。

## 03｜你说“有风险”，那风险到底在哪里？

为了继续推进，我不只是解释接口原理，还拿出了业务场景、功能说明和实际示例。

我甚至专门向领导请示，希望先在我们部门范围内使用。

如果对方真正关注安全，下一步完全可以要求一份清单：

| 需要审查的问题 | 可以形成的具体结论 |
| --- | --- |
| 申请了哪些 API？ | 明确读取、写入、删除能力 |
| 用应用身份还是用户身份调用？ | 确定授权边界 |
| 可以访问哪些业务资源？ | 确定数据影响范围 |
| 数据是否经过外部服务器？ | 评估传输、留存与泄露风险 |
| 如何保存密钥、记录审计日志？ | 落实控制措施 |

这才叫把风险从一句空话变成可以验证的技术问题。

但实际讨论反复回到一句笼统的“存在泄露风险”。

我当然承认：**开放 API 有风险。**

但是，服务器开远程访问有风险，文件共享有风险，电子邮件有风险，外部 SaaS 有风险，甚至一台员工电脑连接内网也有风险。

难道解决办法是全部不让用吗？

所谓安全能力，应该体现在知道风险发生的条件，知道怎样收紧权限，知道怎样设置审计和应急措施。

**如果一种评审方法永远只有“不批准”这一个安全结果，那么它降低的可能是业务活动，而不一定是系统的真实风险。**

## 04｜连审批流程，都能把“权限”和“所有权”搞混

钉钉开放平台原本有相应的权限申请、授权和管理员同意机制。

企业再增加一层内部审批当然不是绝对不行，涉及敏感数据时，也可能有业务和合规意义。

但流程至少应该说明：为什么需要额外审批，谁审核什么，最终以哪些证据决定通过或拒绝。

我们遇到的情况，却是还得走另一张自定义审批表单。

更令人困惑的是，沟通过程中还提出一个要求：

**把开放应用所有权转给信息部人员，再把我设置为管理员。**

问题是：应用所有权、应用管理员、API 权限、数据访问范围，从来都不是一个概念。

如果企业希望统一管理应用资产，要求公司控制应用所有权，这可以讨论。

但如果目的是判断某项接口权限是否安全，所有权转过去，并不会自动回答“谁能读取哪一张表”。

权限评审不是抢应用所有权。

把钥匙拿到自己手上，也不代表你终于明白这把钥匙能打开哪扇门。

## 05｜谈费用可以，至少先把费用算明白

对方还提出：数据量增加后，钉钉成本会越来越高。

这个问题可以谈，而且应该谈。

已有专业版不代表所有接口无限免费。我原本以为不会额外产生费用，也需要根据当时套餐、API 配额和调用量重新核实。

但费用讨论总不能止步于“未来可能很贵”。

要审查成本，至少要有：

- 预计每天调用多少次；
- 当前套餐给多少免费额度；
- 超额按什么规则收费；
- 哪些操作可以批量处理，减少调用次数。

**没有调用量，没有价格规则，没有成本计算，却直接用“以后费用高”否决方案，这不是费用分析，是费用想象。**

正确的结论可以是“需要限制调用量”，可以是“先试点一个月”，也可以是“超过预算后暂停”。

但总得先算。

## 06｜官方 API 怕泄露，来路不明的 Claude 中转却敢推荐

如果前面的事情只是让人无语，接下来这件事就更有反差了。

有人问我：

为什么要代理访问官方 Claude？第三方中转也能用，不是也能写个后端、做 HTTP 响应吗？

关键是，对方说的并非经过企业采购和安全审查的服务，而是随手找来的第三方渠道，连发票都不能提供。

我不认为所有第三方 AI 服务都不安全。正规服务商完全可能提供可靠的 API。

问题在于，当你准备把企业代码、接口信息甚至调试内容交给一个陌生中转平台时，至少应该问问：

**服务是谁运营的？数据去了哪里？请求会不会被记录？上游模型如何提供？出了泄露事故谁负责？**

不能开发票本身不能证明技术不安全，但它至少提示采购合规、合同责任和供应商身份还有问题要核实。

这件事与之前的钉钉审批摆在一起，就很讽刺了。

| 面对官方企业开放平台 | 面对陌生的模型中转 |
| --- | --- |
| 反复担心潜在泄露 | 有人建议“能用就行” |
| 对 API 权限缺乏具体分析 | 对数据流向也没有具体说明 |
| 增加额外审批程序 | 没看到同等严格的供应商审查 |
| 功能和成本被笼统否定 | 技术可用性反而成为主要理由 |

我不能保证这代表部门统一政策，也不认为每位同事都持同一种观点。

但这种出现在同一工作环境里的安全判断反差，确实让人难以信服。

**对自己不熟悉的平台无限放大风险，对听说能用的服务却忽略风险——这不是零信任，是选择性信任。**

## 07｜全公司共用一套 Windows 文件服务器账号

再说一个比“懂不懂 API”更实在的问题。

公司 Windows 文件共享服务器，所有员工登录时使用**同一个用户名、同一个密码**。

这里也必须说清一个事实：普通员工确实可以看到其他部门的文件夹，但打开或修改时会提示无权限。

所以，我不会声称全公司所有文件都能够被任意员工修改。

它至少说明系统存在某种访问拒绝机制。

问题在于，**这套部门隔离具体靠什么实现？**

标准的 Windows SMB 文件共享需要结合实际认证身份、共享权限和 NTFS 权限判断访问资格。如果全员最终真的以相同 Windows 身份访问同一份资源，在其他限制条件也相同时，服务器通常无法单凭这个身份判断当前员工属于哪个部门。

可能有其他身份、设备或网络层的限制，这需要管理员实际核查。我没有服务器配置权限，不能凭感觉替它判定合格或不合格。

但是，所有人共用一套登录凭据，本身就是一项需要整改的身份治理缺陷：

1. 知道密码的人越多，凭据泄露面越大。
2. 离职人员如果仍掌握有效公共凭据，撤销其访问资格会更困难。
3. 审计日志若只记录同一个公共账号，追溯具体操作者就需要结合终端、IP 和其他日志。
4. 一旦某台电脑感染勒索软件，其已有共享文件写入权限可能被恶意程序利用。

尤其是第四条。

假设某台员工电脑已经连接部门共享目录，并且拥有文件修改权限，那么恶意程序可能通过 SMB 远程修改或加密其有权写入的文件。

**文件服务器上的共享文件被加密，不代表服务器操作系统本身一定中毒。**

这也是为什么我不接受“所有服务器都中了病毒”这样一句话就当完整事故报告。

它可能是真的，但需要证据。

同样，这套共用凭据是否参与了本次攻击，目前也没有证据。

可我至少能确定：**一家刚刚遭遇勒索软件事故的企业，应该认真检查这种全员共享凭据的设计，而不是把它视为理所当然。**

微软关于 [SMB 身份认证](https://learn.microsoft.com/en-us/windows/win32/fileio/microsoft-smb-protocol-authentication) 和 [文件共享审计](https://learn.microsoft.com/en-us/windows/security/threat-protection/auditing/audit-file-share) 的文档，已经把相关机制讲得很清楚。

## 08｜不知道 API 是什么，却能参与否决 API 方案

还有一些更基础的交流。

讨论电商 ERP 接口、淘宝开放平台 API 时，我遇到过相关人员对 API 基本概念都讲不清楚的情况。

这里不妨把话说公平。

我不要求网络工程师一定会写业务系统，也不要求擅长服务器虚拟化的人精通电商平台接口。

技术分工很正常。网络、开发、数据库、信息安全、工业控制、企业应用，本来就是不同专业方向。

一个人经常用虚拟机、华为 eNSP 模拟器，或者用 AI 工具查资料，也不能因此推断他技术差。工具没有问题，方向不同更不是问题。

**真正的问题在于，不熟悉一项技术，却要负责审批它；解释了多遍仍没有形成具体技术问题，却依然能够给出否决意见。**

不懂，可以查文档。

还不懂，可以叫供应商、开发人员一起评估。

专业技术人员不应该靠“什么都知道”证明自己，而应该知道什么是自己尚未掌握的，怎样查证，怎样做出有依据的决定。

我不怕别人说“这个我没做过，需要确认一下”。

我怕的是根本不知道自己不知道什么，却已经坚信方案不安全、没价值、成本太高。

## 09｜安全管理不能只体现在审批表单上

回头看看这些经历，会发现同一种反差：

对新的企业应用，审核很严格。

但在已经存在的系统和流程里，仍然能看到全员共享凭据、第三方服务评估薄弱、关键业务恢复困难等现实问题。

这并不代表这些问题都由同一个员工造成，也不代表这次攻击就是他们导致的。

但如果一个信息部门承担了企业基础设施、应用授权、软件集成和安全管理等职责，那么评价它时就不能只看“出了多少张审批单”“拒绝过多少申请”。

应该看的是：

| 真正需要的能力 | 可以验证的成果 |
| --- | --- |
| 身份与权限治理 | 个人账号、最小权限、离职停权、审计追踪 |
| API 安全评审 | 具体权限点、授权方式、数据范围、凭据保护 |
| 第三方服务评估 | 服务主体、合同与合规、数据流向、可替代性 |
| 灾难恢复 | 可用备份、恢复演练、明确的恢复目标 |
| 业务连续性 | 关键业务中断时的替代流程与优先级 |
| 事故复盘 | 可核验的受损清单、原因、整改和复验 |

<HighlightBox eyebrow="最荒诞的反差" title="审批表单不是防火墙，拒绝业务需求也不是安全防护措施">
  安全不是把所有陌生技术都拦下来，而是能够解释清楚风险在哪里、需要哪些控制措施，以及为什么某项申请可以通过或必须拒绝。
</HighlightBox>

尤其是出了事故之后。

真正有价值的不是一句“已经恢复”，而是搞清楚：为什么会扩散？备份能不能用？哪些业务缺乏应急替代方案？共享凭据与管理员权限有没有整改？

否则，服务器这次恢复了，下次仍可能在另一个薄弱点上出事。

## 10｜更可怕的不是不懂技术，而是不懂的人掌握技术审批权

写到这里，我想强调一个界限：

我没有证据认定本次勒索软件的入侵入口，也不能仅凭恢复时间给整个技术团队的网络运维能力打分。

但对于亲自经历的企业应用沟通、看到的共享账号制度，以及财务发薪业务受到的持续影响，我有足够理由表达不满。

因为这已经不是某个人偶尔说错一个技术名词。

它反映的是：**组织是否把技术评审权交给具备相应判断能力的人，是否把真正重要的安全问题落实为工程措施。**

一个系统有风险，当然可以拒绝。

但拒绝应该有根据：申请了不必要的全局权限，密钥保管不安全，供应商不可信，成本超预算，或者业务收益不足以覆盖风险。

这些理由我都能接受，也愿意围绕证据讨论。

我不能接受的，是我提供业务场景、解释授权机制、展示接口和使用方式之后，得到的仍然只是一句模糊的“有风险”。

然后，轮到内部文件系统的共享账号、未知中转服务、财务系统的灾备恢复，却看不到同等清楚的安全逻辑。

**这哪里是安全标准？这更像是对自己不懂的东西设置门槛，对自己习惯的东西降低警惕。**

有人会说，为什么对信息部要求这么高？

因为他们拥有技术管理和审批权。

**权力越大，技术判断就越需要证据。**

服务器坏了，可以修。业务系统坏了，可以重建。数据只要有可靠备份，还有机会恢复。

可如果企业始终不能识别哪些人真正懂技术、哪些流程真正能防风险，那它修复的可能只是眼前这一次故障。

> **我不怕技术人员说自己不懂。我怕的是他根本不懂，却坚信自己最懂；更怕公司把决定别人能不能使用技术的权力，交给了这样的人。**

真正需要升级的，恐怕不只是服务器。
