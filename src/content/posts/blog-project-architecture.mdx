## 先看全局：仓库里有四条相互咬合的主线

<section class="sys-board sys-board--map" aria-label="博客仓库全局地图">
  <header class="sys-board-head">
    <div>
      <span class="sys-index">B01 · REPOSITORY MAP</span>
      <strong class="sys-board-title">文件不是散落的目录，而是四条职责明确的系统线</strong>
    </div>
    <p>内容线负责写什么，页面线负责怎么呈现，规则线负责如何维护，交付线负责怎样变成公开站点。</p>
  </header>

  <div class="sys-map-grid">
    <article class="sys-lane sys-lane--content">
      <span>CONTENT · 内容线</span>
      <strong><code>{`src/content/posts/`}</code></strong>
      <p>正式文章和视觉实验都进入同一个 Content Collection，再由分类、标签、系列与公开状态组织。</p>
      <ul>
        <li><code>{`*.mdx`}</code> 保存可版本化正文</li>
        <li><code>{`visual-lab/`}</code> 单独承载 Demo</li>
      </ul>
    </article>

    <article class="sys-lane sys-lane--view">
      <span>VIEW · 页面线</span>
      <strong><code>{`src/pages/`}</code> + <code>{`src/components/`}</code></strong>
      <p>页面文件建立路由，组件与布局建立阅读界面；文章只调用真正需要的展示能力。</p>
      <ul>
        <li><code>{`src/layouts/SiteLayout.astro`}</code> 提供外壳</li>
        <li><code>{`src/styles/global.css`}</code> 维护全局视觉</li>
      </ul>
    </article>

    <article class="sys-lane sys-lane--rule">
      <span>RULE · 规则线</span>
      <strong><code>{`AGENTS.md`}</code> + <code>{`docs/`}</code></strong>
      <p>入口文件提供路由与关键硬边界，开发、写作、视觉和内容索引分别在 docs 中保持单一权威来源。</p>
      <ul>
        <li><code>{`llms.txt`}</code> 帮 Agent 快速判断入口</li>
        <li><code>{`CONTENT_INDEX.md`}</code> 限定参考范围</li>
      </ul>
    </article>

    <article class="sys-lane sys-lane--ship">
      <span>SHIP · 交付线</span>
      <strong><code>{`astro.config.mjs`}</code> + <code>{`.github/workflows/`}</code></strong>
      <p>Astro 在构建期生成静态文件；Actions 在 main 推送或手动触发后构建，再交给 Pages。</p>
      <ul>
        <li><code>{`package.json`}</code> 暴露验证命令</li>
        <li><code>{`dist/`}</code> 是构建产物，不是内容源</li>
      </ul>
    </article>
  </div>

  <div class="sys-legend" aria-label="蓝图线型图例">
    <span><i class="line-solid" aria-hidden="true"></i>实线：生产主链</span>
    <span><i class="line-dashed" aria-hidden="true"></i>虚线：规则约束</span>
    <strong>结论：改动先按职责找到唯一入口，再进入下一层。</strong>
  </div>
</section>

这张地图刻意不展开函数和模板细节。维护者先判断“我在改内容、页面、规则还是交付”，就能避免把写作规范塞进组件、把 Demo 混进正式文章，或把构建产物当源码维护。

## 正式文章、视觉实验和规则文档为什么必须分区

<section class="sys-board sys-board--zones" aria-label="内容分区与边界蓝图">
  <header class="sys-board-head">
    <div>
      <span class="sys-index">B02 · CONTENT ZONES</span>
      <strong class="sys-board-title">三个区域共享仓库，但承担三种完全不同的承诺</strong>
    </div>
    <p>目录边界不是为了整齐，而是让读者内容、设计试验和 Agent 规则不会互相污染。</p>
  </header>

  <div class="sys-zone-map">
    <article class="sys-zone sys-zone--public">
      <div class="sys-zone-title">
        <span>PUBLIC WORK</span>
        <strong>正式文章</strong>
      </div>
      <code>{`src/content/posts/*.mdx`}</code>
      <p>面向读者发布。每篇保留完整 frontmatter，分类只使用生活、实践、教程、视觉实验室中的合法值。</p>
      <div class="sys-zone-check">
        <span>输入</span><b>作者事实与判断</b>
        <span>输出</span><b>可独立阅读的网页作品</b>
      </div>
    </article>

    <div class="sys-boundary">
      <span>不得混放</span>
      <i aria-hidden="true"></i>
      <small>Demo 不冒充正文<br />规则不作为文章发布</small>
    </div>

    <article class="sys-zone sys-zone--lab">
      <div class="sys-zone-title">
        <span>VISUAL LAB</span>
        <strong>视觉实验</strong>
      </div>
      <code>{`src/content/posts/visual-lab/`}</code>
      <p>集中测试组件、复杂排版和视觉模式。它提供参考效果，但不会成为正式文章的固定骨架。</p>
      <div class="sys-zone-check">
        <span>输入</span><b>待验证的表达方式</b>
        <span>输出</span><b>可参考的视觉样板</b>
      </div>
    </article>

    <div class="sys-boundary">
      <span>只做引用</span>
      <i aria-hidden="true"></i>
      <small>规则给正文设边界<br />正文不复制规则全文</small>
    </div>

    <article class="sys-zone sys-zone--docs">
      <div class="sys-zone-title">
        <span>CONTROL DOCS</span>
        <strong>维护规则</strong>
      </div>
      <code>{`AGENTS.md · docs/ · llms.txt`}</code>
      <p>只服务维护与 Agent 路由。详细规则进入 docs，AGENTS.md 保留硬规则，llms.txt 提供快速入口。</p>
      <div class="sys-zone-check">
        <span>输入</span><b>长期维护约束</b>
        <span>输出</span><b>一致的执行路径</b>
      </div>
    </article>
  </div>

  <footer class="sys-verdict">
    <span>BOUNDARY</span>
    <strong>正式文章对读者负责，视觉实验对表达验证负责，规则文档对维护一致性负责。</strong>
  </footer>
</section>

## 规则和索引如何组成维护控制面

<section class="sys-board sys-board--control" aria-label="博客规则控制面蓝图">
  <header class="sys-board-head">
    <div>
      <span class="sys-index">B03 · CONTROL PLANE</span>
      <strong class="sys-board-title">先路由，再读取；只让一个文件成为每类规则的权威来源</strong>
    </div>
    <p>Agent 不需要默认通读整个仓库，而是从任务类型进入最小必需上下文。</p>
  </header>

  <div class="sys-control-flow">
    <article class="sys-control-entry">
      <span>ENTRY</span>
      <strong>新任务</strong>
      <p>先辨认是代码、文章、MDX 视觉还是内容检索。</p>
    </article>
    <i class="sys-arrow" aria-hidden="true"></i>
    <article class="sys-control-router">
      <span>ROUTER</span>
      <strong><code>{`AGENTS.md`}</code> / <code>{`llms.txt`}</code></strong>
      <p>给出读取顺序与硬边界，不承载长示例。</p>
    </article>
    <i class="sys-arrow" aria-hidden="true"></i>
    <div class="sys-control-sources">
      <article>
        <span>CODE</span>
        <strong><code>{`docs/DEV_RULES.md`}</code></strong>
        <p>最小改动、验证与 Git 约定</p>
      </article>
      <article>
        <span>WRITING</span>
        <strong><code>{`docs/writing/`}</code></strong>
        <p>写作、风格与内容索引</p>
      </article>
      <article>
        <span>VISUAL</span>
        <strong><code>{`docs/ARTICLE_VISUAL_SYSTEM.md`}</code></strong>
        <p>整页视觉方案与章节闭环</p>
      </article>
      <article>
        <span>REFERENCE</span>
        <strong><code>{`CONTENT_INDEX.md`}</code></strong>
        <p>先选主题，再只读 1 到 3 篇正文</p>
      </article>
    </div>
  </div>

  <div class="sys-control-rails">
    <div>
      <span>读取原则</span>
      <strong>任务相关 → 必要规则 → 少量参考 → 目标文件</strong>
    </div>
    <div>
      <span>维护原则</span>
      <strong>同一规则只保留一个权威版本，其他文件只做导航。</strong>
    </div>
    <div>
      <span>变更原则</span>
      <strong>只改直接相关文件，不整理或回滚工作区里的其他修改。</strong>
    </div>
  </div>
</section>

这套控制面让 Agent 可参与维护，但不会把 Agent 变成新的内容源。作者事实和项目真实代码仍然是依据；规则只约束怎样读取、修改和验证。

## 一篇文章怎样从想法进入公开内容系统

<section class="sys-board sys-board--pipeline" aria-label="文章从写作到公开的内容流">
  <header class="sys-board-head">
    <div>
      <span class="sys-index">B04 · CONTENT PIPELINE</span>
      <strong class="sys-board-title">默认公开不是省略检查，而是把例外状态说清楚</strong>
    </div>
    <p>新文章默认 <code>{`draft: false`}</code>、<code>{`private: false`}</code>；只有用户明确要求草稿或私密时才切换状态。</p>
  </header>

  <ol class="sys-pipeline">
    <li>
      <span>01 · BRIEF</span>
      <strong>确认主题与读者任务</strong>
      <p>提炼一句话结论、事实素材、专业风格和文章形态。</p>
      <small>产出：视觉简报</small>
    </li>
    <li>
      <span>02 · DESIGN</span>
      <strong>先设计网页作品</strong>
      <p>按读者问题拆 H2；系统、教程和流程文章默认一章一张完整信息图。</p>
      <small>产出：章节蓝图</small>
    </li>
    <li>
      <span>03 · WRITE</span>
      <strong>写入 Content Collection</strong>
      <p>正文进入 <code>{`src/content/posts/`}</code>，frontmatter 对齐 schema 与固定分类。</p>
      <small>产出：MDX 文件</small>
    </li>
    <li>
      <span>04 · VERIFY</span>
      <strong>检查事实与页面</strong>
      <p>审查敏感信息、桌面和移动布局，再执行测试与静态构建。</p>
      <small>产出：可构建页面</small>
    </li>
    <li>
      <span>05 · PUBLISH</span>
      <strong>提交到 main 的发布链</strong>
      <p>推送触发 Actions；线上是否已经更新，必须查看实际运行后才能确认。</p>
      <small>产出：静态站点</small>
    </li>
  </ol>

  <div class="sys-gates">
    <article class="is-pass">
      <span>默认路径</span>
      <strong><code>{`draft: false · private: false`}</code></strong>
      <p>文章通过内容与页面检查后进入公开集合。</p>
    </article>
    <article class="is-hold">
      <span>明确要求暂不发布</span>
      <strong><code>{`draft: true`}</code></strong>
      <p>不进入公开页面；何时公开由用户后续决定。</p>
    </article>
    <article class="is-stop">
      <span>明确要求不进公开站点</span>
      <strong><code>{`private: true`}</code></strong>
      <p>不进入公开列表、详情、RSS 与站内搜索数据；它不是密码保护。</p>
    </article>
  </div>
</section>

## 仓库怎样变成 GitHub Pages 上的静态站点

<section class="sys-board sys-board--release" aria-label="静态构建与发布边界蓝图">
  <header class="sys-board-head">
    <div>
      <span class="sys-index">B05 · RELEASE BOUNDARY</span>
      <strong class="sys-board-title">源码、构建和托管分成三段，线上不需要常驻 Node 服务</strong>
    </div>
    <p>当前配置使用 Astro + MDX。工作流在 main 推送或手动触发时运行，构建完成后由 GitHub Pages 托管静态产物。</p>
  </header>

  <div class="sys-release-track">
    <article>
      <span>SOURCE</span>
      <strong>仓库源码</strong>
      <code>{`posts · pages · components · styles`}</code>
      <p>Git 记录内容与代码的每次变化。</p>
    </article>
    <i aria-hidden="true"></i>
    <article>
      <span>BUILD</span>
      <strong>Astro 静态生成</strong>
      <code>{`npm test\nnpm run build`}</code>
      <p>测试与构建验证由本地或 CI 执行。</p>
    </article>
    <i aria-hidden="true"></i>
    <article>
      <span>DELIVER</span>
      <strong>GitHub Actions</strong>
      <code>{`withastro/action@v6`}</code>
      <p>上传 Pages artifact，deploy job 等待 build。</p>
    </article>
    <i aria-hidden="true"></i>
    <article>
      <span>HOST</span>
      <strong>GitHub Pages</strong>
      <code>{`https://apexcheng.github.io`}</code>
      <p>提供静态文件，不运行应用后端。</p>
    </article>
  </div>

  <div class="sys-release-facts">
    <article>
      <span>仓库可确认</span>
      <strong><code>{`site`}</code> 已配置，未配置 <code>{`base`}</code></strong>
      <p>这与当前用户站点根路径方案一致。</p>
    </article>
    <article>
      <span>仓库可确认</span>
      <strong>工作流权限与并发组已声明</strong>
      <p><code>{`contents: read`}</code>、<code>{`pages: write`}</code>、<code>{`id-token: write`}</code>，并使用 pages concurrency group。</p>
    </article>
    <article class="is-verify">
      <span>需运行验证</span>
      <strong>Pages Source、最新 Actions 运行与线上页面</strong>
      <p>这些属于仓库外实时状态，不能只凭配置文件宣称已经成功。</p>
    </article>
  </div>
</section>

静态架构的取舍也在这里：它没有数据库、登录、在线编辑后台和常驻应用服务，换来的是更短的访问链、更低的运行维护成本，以及可被 Git 审查的内容历史。
