## 先纠正一个旧印象：Hermes 已经不只是本地 CLI 工具箱

旧稿里，我把 Hermes 概括成“本地优先的 agent runtime + 一部分 gateway + tools + skills”。这个理解曾经有帮助，但放到现在已经太窄。

Hermes 的核心仍然是 Agent Runtime：接收任务、组织上下文、调用模型、选择工具、执行动作、保存状态。但围绕这个 Runtime，已经长出一整套完整表面。

  </header>

    </div>
    <div class="hermes-surface__agent">
      <small>RUNTIME</small>
      <strong>Hermes Agent</strong>
      <span>模型推理 · 工具调用 · 规则 · 状态 · 自动化</span>

      <article><b>Memory</b><span>跨会话保留的信息</span></article>
    </div>
  </div>

所以今天更合适的理解是：

> **Hermes 是一套完整的 Agent 运行环境。CLI 是它最直接的入口，但不是它的边界。**

这和 OpenClaw 的差别，也不再是“一个有 Gateway，一个没有 Gateway”。两者现在都有完整运行时、Skills、工具、会话和消息渠道，只是组织方式和使用重心不同。

最重要的差异之一，是 **OpenClaw 的 workspace 是 Agent 的明确“家”**；Hermes 则允许你直接在项目目录里启动 Agent，同时又通过 `hermes project` 和 `hermes profile` 管理更复杂的项目和隔离实例。

所以，旧稿里“Hermes 没有显式 Workspace”的说法现在也应该删除。

## Hermes 实际在做什么：看一条完整运行链路

如果把所有名词都拿掉，一次 Hermes 任务其实只有四层。

<section class="hermes-board hermes-runtime" aria-label="Hermes Agent 运行链路">
  <header class="hermes-board__head">
    <div><span>03 · RUNTIME PATH</span><strong>输入不是重点，关键是任务如何穿过四层系统</strong></div>
    <p>CLI、Desktop 和 Gateway 最终都会进入同一个 Agent 执行逻辑。</p>
  </header>
  <div class="hermes-runtime__track">
    <article><b>01</b><span>INPUT</span><strong>用户任务</strong><p>CLI、TUI、Desktop、Gateway、Cron。</p></article>
    <i>→</i>
    <article class="is-blue"><b>02</b><span>REASON</span><strong>Agent + Model</strong><p>读取规则、上下文和当前 Session，决定下一步。</p></article>
    <i>→</i>
    <article class="is-purple"><b>03</b><span>ACT</span><strong>Tools / Skills / MCP</strong><p>读文件、执行命令、浏览网页、调用外部服务。</p></article>
    <i>→</i>
    <article class="is-green"><b>04</b><span>STATE</span><strong>结果 + Session + Memory</strong><p>返回结果，并把该留下的状态保存下来。</p></article>
  </div>
  <div class="hermes-runtime__note">
    <span>一句话</span>
    <strong>模型负责判断下一步；Tools / MCP 负责真正执行；Skills 负责告诉 Agent 应该怎样做；Session / Memory 负责让下一轮不从零开始。</strong>
  </div>
</section>

这也是理解 Hermes 最重要的一条线：**Tool 和 Skill 绝不是同一个东西，Session 和 Memory 也绝不是同一个东西。**

## 安装：现在不必只盯着 WSL2

旧稿默认“Windows 用户 → WSL2 → 安装 Hermes”。现在官方已经明确支持 macOS、Linux、WSL2、Windows Native，macOS / Windows 还提供 Hermes Desktop 安装器。

如果本来就在 WSL2 里维护代码和 OpenClaw，继续装在 WSL2 完全合理；但它已经不是唯一正确路径。

Linux / macOS / WSL2 的当前官方 CLI 安装命令：

```bash
curl -fsSL https://hermes-agent.nousresearch.com/install.sh | bash
```

Windows Native：

```powershell
iex (irm https://hermes-agent.nousresearch.com/install.ps1)
```

安装后先做最小检查：

```bash
hermes version
hermes doctor
```

然后只处理模型，不要马上接 Gateway、Browser、MCP：

```bash
hermes model
hermes chat -q "Reply with exactly: OK"
```

如果这个最小聊天都不通，继续配置更多能力只会增加变量。

官方安装与 Quickstart：[Installation](https://hermes-agent.nousresearch.com/docs/getting-started/installation/)、[Quickstart](https://hermes-agent.nousresearch.com/docs/getting-started/quickstart)。

## OpenClaw 用户最值得先看的，其实是官方迁移工具

这是旧稿里完全没有、但现在最值得 OpenClaw 用户知道的一项能力。

Hermes 会在首次 `hermes setup` 时检测 `~/.openclaw`，并询问是否查看迁移计划。也可以随时手动执行：

```bash
hermes claw migrate --dry-run
```

这个命令只预览，不写入。

<section class="hermes-board hermes-migrate" aria-label="OpenClaw 迁移到 Hermes 的流程">
  <header class="hermes-board__head">
    <div><span>05 · OPENCLAW MIGRATION</span><strong>不要手工复制配置，先让 Hermes 给出迁移计划</strong></div>
    <p>官方迁移器已经理解两套系统之间大量字段和目录的映射。</p>
  </header>
  <div class="hermes-migrate__flow">
    <article><b>1</b><strong>读取 OpenClaw</strong><span>{'~/.openclaw'}</span><p>识别 persona、memory、skills、provider、MCP、gateway 等配置。</p></article>
    <i>→</i>
    <article class="is-preview"><b>2</b><strong>Dry Run</strong><span>只生成迁移预览</span><p>先看会迁什么、冲突在哪里、什么需要人工处理。</p></article>
    <i>→</i>
    <article class="is-apply"><b>3</b><strong>Apply</strong><span>确认后才写入</span><p>迁移到 `~/.hermes`，冲突按策略处理。</p></article>
  </div>
  <div class="hermes-migrate__split">
    <section>
      <span>可以直接映射</span>
      <strong>SOUL · MEMORY · USER · Skills · Model · MCP · Gateway · Approval 等</strong>
      <p>当前 CLI Reference 已列出 30+ 类迁移项。</p>
    </section>
    <section class="is-review">
      <span>需要归档 / 人工复核</span>
      <strong>Cron · Plugins · Hooks · Multi-Agent · 部分 UI / Identity 等</strong>
      <p>没有可靠一一对应的内容不会硬塞进 Hermes。</p>
    </section>
  </div>
  <footer><b>安全默认值：</b>即使使用 `full` preset，也不会自动迁移 secrets；只有显式加 `--migrate-secrets` 才会包含密钥。</footer>
</section>

我更建议的路径是：

```bash
# 1. 只看计划
hermes claw migrate --dry-run

# 2. 只迁用户数据，不碰 secrets
hermes claw migrate --preset user-data
```

如果确实准备把现有 OpenClaw 配置完整迁过去，再查看 `hermes claw migrate --help`，逐项决定 provider、gateway、skills 冲突和 workspace instruction 怎么处理。

官方文档：[Migrate from OpenClaw](https://hermes-agent.nousresearch.com/docs/guides/migrate-from-openclaw)。

## Model / Provider / OAuth：不要把这三个概念揉成一个

OpenClaw 用户通常已经习惯“Provider + Model”。Hermes 还多了一层非常显眼的 Auth 管理。

现在最简单的原则是：

<section class="hermes-board hermes-model" aria-label="Hermes 模型与认证关系">
  <header class="hermes-board__head">
    <div><span>06 · MODEL & AUTH</span><strong>选谁提供推理、选哪个模型、凭什么登录，是三件事</strong></div>
    <p>多数配置都应该先从 `hermes model` 进入，而不是手改 YAML。</p>
  </header>
  <div class="hermes-model__columns">
    <article><span>PROVIDER</span><strong>谁提供推理</strong><p>Nous Portal、OpenRouter、Anthropic、OpenAI API、Gemini、Copilot、自建 endpoint……</p></article>
    <i>+</i>
    <article><span>MODEL</span><strong>具体用哪个模型</strong><p>同一个 Provider 下面可以切换多个模型，也可以做 fallback / routing。</p></article>
    <i>+</i>
    <article><span>AUTH</span><strong>凭什么访问</strong><p>API Key、OAuth、device code、credential pool 等。</p></article>
  </div>
  <div class="hermes-model__paths">
    <section><b>A</b><strong>Nous Portal</strong><span>`hermes setup --portal`</span><p>一次 OAuth 配好模型入口和 Tool Gateway。适合已经使用 Nous Portal 的用户。</p></section>
    <section><b>B</b><strong>OAuth Provider</strong><span>`hermes model`</span><p>Codex、Anthropic、Copilot、Qwen、MiniMax 等支持对应 OAuth 流程。</p></section>
    <section><b>C</b><strong>API Key / 自建</strong><span>`hermes model` / `.env`</span><p>OpenRouter、Gemini、DeepSeek、OpenAI-compatible endpoint 等。</p></section>
  </div>
</section>

这里有一个非常容易混淆的地方：

- `hermes model`：终端外执行。负责**新增 Provider、OAuth 登录、录入 API Key、选择模型**。
- `/model`：Hermes 会话里面执行。只负责**在已经配置好的模型之间切换**。
- `hermes auth`：更偏**凭据池和认证状态管理**，不是普通用户第一次配置模型的首选入口。

所以旧笔记里把 OpenAI Codex 的主流程写成 `hermes auth add openai-codex`，现在不应该继续保留。当前更稳定的入口是：

```bash
hermes model
```

在模型向导里选择 ChatGPT / Codex Subscription，并完成 OAuth。

官方 Provider 文档：[AI Providers](https://hermes-agent.nousresearch.com/docs/integrations/providers)。

## Tools、Skills、MCP：一个负责做，一个负责教，一个负责扩展

这是最需要讲清楚的一组概念。

<section class="hermes-board hermes-capability" aria-label="Tools Skills MCP 三者区别">
  <header class="hermes-board__head">
    <div><span>07 · CAPABILITY LAYERS</span><strong>Tool 能执行，Skill 能指导，MCP 能把外部能力接进来</strong></div>
    <p>三者最终都会影响 Agent 能不能完成任务，但工作层级完全不同。</p>
  </header>
  <div class="hermes-capability__grid">
    <article class="is-tool">
      <span>TOOL</span>
      <strong>真正产生动作</strong>
      <p>terminal、file、web、browser、memory、cron、delegation……</p>
      <small>像 OpenClaw 的 tools / exec / browser</small>
    </article>
    <article class="is-skill">
      <span>SKILL</span>
      <strong>告诉 Agent 应该怎么做</strong>
      <p>按需加载 `SKILL.md`，提供领域知识、流程、规则和工具使用方法。</p>
      <small>不是“执行函数”，而是任务知识</small>
    </article>
    <article class="is-mcp">
      <span>MCP</span>
      <strong>把外部工具接进来</strong>
      <p>GitHub、数据库、公司服务、文件系统、第三方工具服务器。</p>
      <small>外部能力进入 Hermes 的标准桥梁之一</small>
    </article>
  </div>
  <div class="hermes-capability__example">
    <span>例子</span>
    <strong>“帮我修这个仓库里的 Bug”</strong>
    <i>→</i>
    <div><b>Skill</b> 先告诉 Agent 项目规则和排查方法</div>
    <i>→</i>
    <div><b>Tool</b> 读文件、执行测试、修改代码</div>
    <i>→</i>
    <div><b>MCP</b> 如果需要，再调用 GitHub 或外部系统</div>
  </div>
</section>

常用查看命令：

```bash
hermes tools --summary
hermes skills list
hermes skills search <keyword>
hermes mcp
```

当前 Hermes 的 Skills 已经不仅是“本地放一份 SKILL.md”。CLI 支持 browse、search、inspect、install、update、audit、publish，也有 Skill 写入审批和 curator 等机制。

MCP 也比旧稿成熟得多。Hermes 可以作为 MCP Client 连接 stdio / HTTP server，也可以执行：

```bash
hermes mcp serve
```

把自己的消息会话能力暴露成 MCP server，给其他 Agent 使用。

另外，旧稿中 MCP 工具名举例写成了 `mcp_github_create_issue`。当前官方规则是类似：

```text
mcp__server_name__tool_name
```

例如 server 名和 tool 名中的特殊字符会被清洗后注册。

官方文档：[Tools & Toolsets](https://hermes-agent.nousresearch.com/docs/user-guide/features/tools/)、[MCP](https://hermes-agent.nousresearch.com/docs/user-guide/features/mcp)。

## Session 和 Memory：一个负责“这次聊到哪”，一个负责“以后还记得什么”

这两个概念经常被写在一起，实际应该分开。

<section class="hermes-board hermes-state" aria-label="Session 和 Memory 的区别">
  <header class="hermes-board__head">
    <div><span>08 · STATE MODEL</span><strong>Session 是运行上下文，Memory 是跨会话知识</strong></div>
    <p>“没有清空聊天”不等于长期记忆；“写进 Memory”也不等于永远把全部内容塞进当前上下文。</p>
  </header>
  <div class="hermes-state__split">
    <article>
      <span>SESSION</span>
      <strong>这一段对话进行到哪里</strong>
      <ul>
        <li>保存消息、模型、工具调用和会话状态</li>
        <li>Gateway 中按聊天来源路由</li>
        <li>可以 browse、resume、rename、export、prune</li>
        <li>当前主存储以 `~/.hermes/state.db` 为核心</li>
      </ul>
      <code>hermes sessions browse</code>
    </article>
    <article class="is-memory">
      <span>MEMORY</span>
      <strong>跨 Session 仍值得保留什么</strong>
      <ul>
        <li>内置 `MEMORY.md` / `USER.md` 始终可用</li>
        <li>可叠加一个外部 Memory Provider</li>
        <li>外部 Provider 是增强，不会替代内置 Memory</li>
        <li>适合稳定偏好、项目事实、长期知识</li>
      </ul>
      <code>hermes memory status</code>

```bash
hermes sessions list

hermes sessions stats
```

管理外部 Memory Provider：

当前官方文档列出的外部 Memory Provider 包括 Honcho、OpenViking、Mem0、Hindsight、Holographic、RetainDB、ByteRover、Supermemory 等；同时只激活一个外部 Provider，内置 Memory 始终继续工作。

官方文档：[Memory Providers](https://hermes-agent.nousresearch.com/docs/user-guide/features/memory-providers/)。

如果已经把 OpenClaw 当作一个“消息渠道 ↔ Agent Runtime”的统一入口，那么 Hermes Gateway 很容易理解。

## 到底什么时候用 Hermes，什么时候继续用 OpenClaw？

我不建议把这个问题理解成“谁替代谁”。更实用的判断是：**你当前想优化的是哪一层。**

<section class="hermes-board hermes-decision" aria-label="Hermes 与 OpenClaw 使用场景选择">
  <header class="hermes-board__head">
    <div><span>10 · DECISION MAP</span><strong>不是二选一，而是看现有系统哪一套更接近你的工作中心</strong></div>
    <p>两边能力已经高度重叠，迁移成本和既有生态往往比功能清单更重要。</p>
  </header>
  <div class="hermes-decision__grid">
    <article class="is-hermes">
      <span>更值得试 Hermes</span>
      <strong>你想重新搭一套 Agent 工作环境</strong>
      <ul>
        <li>希望 CLI / Desktop / Gateway 用同一套 Hermes 状态</li>
        <li>重视多 Provider / OAuth / Profile / Project</li>
        <li>想使用 Hermes 当前的 Skills、Plugins、Memory Provider 生态</li>
        <li>希望直接用官方 `hermes claw migrate` 迁移 OpenClaw 数据</li>
      </ul>
    </article>
    <article class="is-openclaw">
      <span>继续用 OpenClaw</span>
      <strong>现有体系已经稳定运行</strong>
      <ul>
        <li>现有 workspace、skills、gateway、channels 已经形成稳定习惯</li>
        <li>大量项目规则和自动化已经围绕 OpenClaw 构建</li>
        <li>当前没有明确痛点，不需要为了“换 Agent”重新迁移运维体系</li>
        <li>更重视稳定延续，而不是尝试另一套运行环境</li>
      </ul>
    </article>
  </div>
  <div class="hermes-decision__verdict">
    <span>最小成本策略</span>
    <strong>先并行试用，再决定迁移。</strong>
    <p>用 Hermes 跑一个真实项目，体验模型、Tools、Skills、Session 和 Gateway；确认确实更适合，再对 OpenClaw 做 dry-run migration，而不是先删掉旧系统。</p>
  </div>
</section>

如果已经是 OpenClaw 重度用户，我会先做下面这组最小实验：

```bash
# 1. 安装并跑通模型
hermes model
hermes chat -q "检查当前目录，并总结这个项目是做什么的"

# 2. 看工具边界
hermes tools --summary

# 3. 看 OpenClaw 迁移计划，但暂时不写入
hermes claw migrate --dry-run

# 4. 确认真正想迁的内容，再决定是否执行
```

这样你得到的不是一张“功能对比表”，而是一次真实体验：**Hermes 在你的工作流里，到底能不能比现有 OpenClaw 更顺。**
