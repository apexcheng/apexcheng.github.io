把多个 Agent 都接到同一个 Chrome，并不等于让它们共享同一个任务。真正应该被共享的是运行时：一个可见的真实 Chrome、一个固定 Profile、一条固定 CDP 通道和一套可恢复的生命周期。每个业务任务仍只拥有自己的页面、选择器与结果。

  <div>
    <span>SHARED CHROME RUNTIME · FIELD GUIDE</span>
    <h2>先保证浏览器活着、可连接、可复用；再让 Agent 处理网页业务。</h2>
    <p>Browser Agent 把 Chrome 的启动与恢复从 Skill 中拿走。接入方只做两件事：调用 <code>ensure</code>，再连接 CDP。</p>
  </div>
  <ol>
    <li><b>01</b><span>固定 Profile</span><em>登录状态有唯一归属</em></li>
    <li><b>02</b><span>固定 CDP</span><em>连接地址不再由项目各自分配</em></li>
    <li><b>03</b><span>独立 Page</span><em>任务只关闭自己创建的页面</em></li>
    <li><b>04</b><span>显式边界</span><em>默认串行，不把共享当作并发能力</em></li>

## 先分清：谁管理运行时，谁完成网页任务

Browser Agent 不是采集器，也不是远程浏览器集群。它只在一台可执行本地命令的机器上管理 Chrome 进程、共享 Profile 和 CDP。业务 Skill 或 Python 项目负责进入网站、读取页面、提交表单或提取数据。

<section class="runtime-board runtime-layers" aria-label="Browser Agent 分层架构">
  <header>
    <span>01 · RESPONSIBILITY MAP</span>
    <h3>共享的是底座，不是页面控制权</h3>
    <p>把生命周期和业务逻辑拆开后，故障归属与关闭权限也随之清晰。</p>
  </header>
  <div class="layer-stack">
    <article class="layer-task">
      <b>业务层</b>
      <strong>Skill / Python / 本地 AI Agent</strong>
      <p>调用 <code>ensure</code>、连接 CDP、创建自己的 <code>page</code>，执行该网站的选择器和业务逻辑。</p>
    </article>
    <div class="layer-arrow">↓ 连接，不启动自己的浏览器</div>
    <article class="layer-control">
      <b>控制层</b>
      <strong><code>~/browser-agent/browser-agent</code></strong>
      <p>提供 <code>ensure</code>、<code>status</code>、<code>connect</code>、<code>disconnect</code>、<code>stop</code> 等统一入口；页面命令会先确保浏览器可用。</p>
    </article>
    <div class="layer-arrow">↓ 健康检查与恢复</div>
    <article class="layer-runtime">
      <b>运行时层</b>
      <strong>真实 Google Chrome + 固定 Profile + 固定 CDP</strong>
      <p>保存登录状态与浏览器配置，并通过 <code>http://127.0.0.1:19312</code> 暴露调试连接。</p>
    </article>
  </div>
  <footer><b>职责边界：</b>控制层负责“浏览器是否可用”；业务层负责“这个网页任务做什么、是否成功”。两边都不替对方猜测。</footer>
</section>

这样可以消除常见的重复劳动：每个项目各自寻找 Chrome、各自创建临时 Profile、各自抢端口、连接失败后各自重启进程。只要业务脚本遵守“只关闭自己 Page”的规则，任务结束时就不会主动带走其他任务仍在复用的共享 Chrome。

## 固定约定是一份连接合同

这套工具的当前默认配置将运行时放在用户目录下，使用本机回环地址的 19312 端口。上游配置的 Chrome 可执行文件默认值是 macOS 的 Google Chrome 路径；若部署在其他系统，必须通过配置确认可执行文件路径，而不是照抄默认值。

<section class="runtime-board runtime-contract" aria-label="Browser Agent 固定连接合同">
  <header>
    <span>02 · CONNECTION CONTRACT</span>
    <h3>让每个接入方说同一种语言</h3>
    <p>路径与端口是运行时边界；Profile 本身承载登录态，不能当作普通项目文件。</p>
  </header>
  <dl>
    <div><dt>控制入口</dt><dd><code>&#126;/browser-agent/browser-agent</code><small>所有 Agent 与本地项目的统一命令入口。</small></dd></div>
    <div><dt>共享 Profile</dt><dd><code>&#126;/browser-agent/chrome-profile</code><small>Cookie、本地存储和浏览器配置的持久化位置。</small></dd></div>
    <div><dt>CDP 地址</dt><dd><code>http://127.0.0.1:19312</code><small>Playwright 与命令行工具连接既有 Chrome 的回环地址。</small></dd></div>
    <div><dt>默认会话</dt><dd><code>browser-agent</code><small>Playwright CLI 的会话名；可临时覆盖，但仍连接同一 Profile。</small></dd></div>
  </dl>
  <div class="contract-note"><b>安全含义</b><span>Profile 中可能包含登录凭据与站点状态：不要提交到 Git，不要把目录打包给不受信任的环境，也不要把 CDP 暴露到非本机网络。</span></div>
</section>

如果要自定义路径、端口或会话名，先检查 <code>config.env</code> 中的 <code>CHROME_BIN</code>、<code>CDP_PORT</code> 与 <code>BROWSER_AGENT_SESSION</code>。修改后是否仍能启动和连接属于运行环境事实，需运行验证。

## `ensure` 把“能否连接”收敛为一个状态机

业务代码不应该先猜 Chrome 是否已启动。它应当把判断交给 <code>ensure</code>：脚本先访问 <code>/json/version</code>，再根据共享 Profile 进程与端口状态决定复用、报错或恢复。

```bash
~/browser-agent/browser-agent ensure
```

        <i aria-hidden="true">↓</i>

        <i aria-hidden="true">↓</i>
        <strong class="state-end">CDP 就绪 · ensure 结束</strong>
      </section>
    </div>
  </div>
  <footer><b>明确失败：</b>按当前脚本实现，CDP 已响应但找不到匹配的 Profile 进程，或端口检查发现 19312 被其他程序占用时，<code>ensure</code> 会报错，而非接管一个身份未知的浏览器。</footer>
</section>

这里有一个很重要的边界：<code>ensure</code> 解决的是“Chrome/CDP 是否可用”，不是“页面是否加载成功”“Cookie 是否过期”或“验证码是否已处理”。后几项仍要由业务任务观察并在需要时交给人处理。

## 接入顺序：保证运行时，再拥有自己的页面

外部 Python 项目最小接入步骤是：先运行 <code>ensure</code>，再以 CDP 附着到 Chrome；从已有 context 中新建页面；完成后只关闭该页面。下面的代码保留了连接与关闭边界，适合作为业务脚本的起点。

<section class="runtime-board runtime-sequence" aria-label="外部项目接入顺序">
  <header>
    <span>04 · ATTACH SEQUENCE</span>
    <h3>每个任务都从同一个入口进入，却只带走自己的 Page</h3>
    <p>CDP 连接附着的是已有 Chrome；它不应被业务任务当成私有浏览器来关闭。</p>
  </header>
  <ol>
    <li><b>1</b><strong>确保</strong><span>调用 <code>browser-agent ensure</code>。</span></li>
    <li><b>2</b><strong>附着</strong><span><code>connect_over_cdp()</code> 连接固定地址。</span></li>
    <li><b>3</b><strong>隔离</strong><span>从既有 context 新建本任务的 <code>page</code>。</span></li>
    <li><b>4</b><strong>收尾</strong><span>关闭该 <code>page</code>，保留 context、browser 与 Chrome。</span></li>
  </ol>
</section>

```python
import subprocess
from pathlib import Path

from playwright.sync_api import sync_playwright


browser_agent = Path.home() / "browser-agent" / "browser-agent"

subprocess.run([str(browser_agent), "ensure"], check=True)

with sync_playwright() as playwright:
    browser = playwright.chromium.connect_over_cdp(
        "http://127.0.0.1:19312"
    )
    context = browser.contexts[0]
    page = context.new_page()

    try:
        page.goto("https://example.com")
        # 只写当前项目的网站业务逻辑。
    finally:
        page.close()
```

如果该运行时没有可用 context，或 CDP 协议与客户端版本不兼容，上面示例会失败；这是接入环境而非网页业务本身的问题，需运行验证后再决定如何处理。

## 复用登录态，不复用页面控制权

同一 Profile 让不同任务看见同一份登录状态。上游规则仍明确要求默认不要并发操作，并让不同任务各自创建页面；因此页面隔离只是最低限度的协作约定，不是多租户安全边界。

<section class="runtime-board runtime-isolation" aria-label="共享与隔离边界矩阵">
  <header>
    <span>05 · SHARE / ISOLATE</span>
    <h3>一份身份状态，多个独立任务页面</h3>
    <p>先识别什么被共享，才能避免把“新建页面”误当成账号或业务隔离。</p>
  </header>
  <div class="isolation-grid">
    <article class="isolation-shared"><b>共享</b><strong>Chrome 进程、Profile、Cookie、Local Storage、CDP 地址</strong><p>它们由运行时维护，通常在任务结束后持续存在。</p></article>
    <article class="isolation-owned"><b>任务独有</b><strong>本任务创建的 Page、选择器、导航与结果</strong><p>任务负责关闭自己的页面，并把结果写回自己的业务上下文。</p></article>
    <article class="isolation-forbidden"><b>不要触碰</b><strong><code>context.close()</code>、<code>browser.close()</code>、未授权的 <code>stop</code></strong><p>这些动作会影响共享运行时与其他任务，应保留给明确授权的运维操作。</p></article>
  </div>
  <div class="isolation-rule"><span>并发规则</span><b>默认同一时刻只让一个 Agent 操作共享 Chrome。</b><p>即使以不同 <code>BROWSER_AGENT_SESSION</code> 连接，它们依然控制同一 Profile；会话名不等于浏览器隔离。</p></div>
</section>

验证码、扫码和账号安全验证不应尝试绕过。让用户在可见的 Chrome 中完成验证，再继续运行任务。对有写入、副作用或资金风险的网站，业务层还应自行设计确认、幂等和结果复核；Browser Agent 不替代这些控制。

## 日常命令：先看状态，再做可定位的动作

除了给 Python 接入，控制入口还封装了 Playwright CLI 的常用页面操作。它会在需要时附着到 CDP；其中 <code>start</code> 当前是 <code>ensure</code> 的别名，<code>close</code> 被显式拒绝，以避免误关共享 Chrome。

<section class="runtime-board runtime-runbook" aria-label="Browser Agent 操作清单">
  <header>
    <span>06 · OPERATOR RUNBOOK</span>
    <h3>把“连上了”变成可检查的日常操作</h3>
    <p>页面已经跳转、刷新或弹窗变化后，应重新获取快照；旧引用不应继续假定有效。</p>
  </header>
  <div class="runbook-grid">
    <div><code>browser-agent ensure</code><span>保证共享 Chrome 与 CDP 可用。</span></div>
    <div><code>browser-agent status</code><span>查看当前运行状态。</span></div>
    <div><code>browser-agent snapshot</code><span>读取最新页面结构与引用。</span></div>
    <div><code>browser-agent click e12</code><span>按最新快照中的引用执行操作。</span></div>
    <div><code>{'browser-agent fill e20 "文本"'}</code><span>填写指定引用对应的输入区域。</span></div>
    <div><code>browser-agent screenshot</code><span>保留页面可视证据。</span></div>
    <div><code>browser-agent disconnect</code><span>只断开 CLI 会话，不关闭 Chrome。</span></div>
    <div><code>browser-agent stop</code><span>仅在用户明确要求关闭共享浏览器时使用。</span></div>
  </div>
</section>

`snapshot`、`click`、`fill` 中的引用值取决于当时的页面结构，示例里的 <code>e12</code> 与 <code>e20</code> 不是可跨页面复用的固定选择器。实际页面命令、登录状态和站点反馈均需运行验证。

## 出现故障时，按影响范围回到正确层级

<section class="runtime-board runtime-triage" aria-label="Browser Agent 故障分流">
  <header>
    <span>07 · FAILURE TRIAGE</span>
    <h3>不要用重启 Chrome 处理所有问题</h3>
    <p>先判断异常发生在运行时、连接、页面还是账号验证，再把动作限制在对应层级。</p>
  </header>
  <div class="triage-grid">
    <article><b>CDP 不可达</b><strong>先执行 <code>ensure</code></strong><p>若仍失败，检查端口占用、Chrome 可执行文件、Profile 权限和脚本输出。</p></article>
    <article><b>能连上但页面异常</b><strong>重新 snapshot，检查 URL 与页面状态</strong><p>这是网站或任务逻辑问题；不要仅因元素找不到就结束共享 Chrome。</p></article>
    <article><b>登录失效或出现验证码</b><strong>停在可见 Chrome，交给用户</strong><p>登录状态保存在 Profile，但过期与安全验证仍是站点的业务边界。</p></article>
    <article><b>多个 Agent 相互干扰</b><strong>停止并发，明确串行所有者</strong><p>不同 CLI 会话不提供页面或身份隔离；先完成当前任务再交接。</p></article>
  </div>
  <footer><b>最终原则：</b>共享运行时降低重复维护成本，但不取消操作授权、网站规则、人工验证和业务结果复核。</footer>
</section>

<div class="runtime-summary"><span>TAKEAWAY</span><strong>把 Chrome 当作受管理的本地基础设施：入口统一、身份固定、连接可恢复、页面各自负责；只要不越过共享边界，业务 Agent 就能把精力放在网页任务本身。</strong></div>
