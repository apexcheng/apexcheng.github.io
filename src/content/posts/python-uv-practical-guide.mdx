刚开始写 Python 时，很多人以为“装好 Python，再 `pip install` 几个包”就够了。等项目稍微多一点，很快会遇到另一组问题：这次到底用了哪个 Python？包被装进了哪个环境？换一台电脑为什么版本不一样？`requirements.txt`、虚拟环境和锁文件分别该谁维护？

`uv` 的价值不是把 `pip` 换成一个更快的命令，而是把这些原本分散的事情收回到同一套项目工作流里：**Python 解释器、项目依赖、虚拟环境、锁文件和运行命令，可以由一个工具统一协调。**

## uv 到底解决了什么

先把几个经常混在一起的东西拆开。

<div class="uv-system-map" aria-label="Python 解释器、项目、依赖和环境之间的关系">
  <div class="uv-system-top">
    <div>
      <span>01</span>
      <strong>Python 解释器</strong>
      <p>真正执行 `.py` 代码的程序，例如 Python 3.12。</p>
    </div>
    <div>
      <span>02</span>
      <strong>项目依赖</strong>
      <p>代码额外需要的包，例如 requests、pandas。</p>
    </div>
    <div>
      <span>03</span>
      <strong>项目环境</strong>
      <p>把这个项目需要的 Python 和包隔离起来，通常就是 `.venv`。</p>
    </div>
  </div>
  <div class="uv-system-controller">
    <div class="uv-logo-word">uv</div>
    <div>
      <strong>统一协调层</strong>
      <p>选择 / 安装 Python，读取项目依赖，解析精确版本，同步 `.venv`，再在正确环境里执行命令。</p>
    </div>
  </div>
  <div class="uv-system-files">
    <div><code>.python-version</code><span>项目希望使用哪个 Python</span></div>
    <div><code>pyproject.toml</code><span>项目需要什么依赖</span></div>
    <div><code>uv.lock</code><span>最终解析成哪些精确版本</span></div>
    <div><code>.venv/</code><span>当前电脑真正安装好的项目环境</span></div>
  </div>
</div>

这里最容易混淆的一点是：**“安装 Python”和“安装 Python 包”完全不是一回事。**

```text
uv python install 3.12
        ↓
安装的是 Python 解释器

uv add pandas
        ↓
安装的是项目要用的第三方包，并把依赖写进项目配置
```

如果只记住这一条，后面很多环境问题都会少一半。

## 它和 pip、venv、pyenv、pip-tools 是什么关系

传统 Python 工具链经常是“每个工具管一段”：

<div class="uv-compare" aria-label="传统 Python 工具链与 uv 项目工作流对比">
  <div class="uv-compare-side is-old">
    <span class="uv-label">传统组合</span>
    <div class="uv-tool-row"><b>pyenv / 系统安装器</b><span>管理 Python 版本</span></div>
    <div class="uv-tool-row"><b>venv / virtualenv</b><span>创建隔离环境</span></div>
    <div class="uv-tool-row"><b>pip</b><span>安装 Python 包</span></div>
    <div class="uv-tool-row"><b>pip-tools</b><span>把依赖解析并锁定</span></div>
    <div class="uv-tool-row"><b>python / pytest</b><span>自己确认环境后运行</span></div>
  </div>
  <div class="uv-compare-arrow">→</div>
  <div class="uv-compare-side is-new">
    <span class="uv-label">uv 项目模式</span>
    <div class="uv-unified">
      <strong>uv</strong>
      <p>Python 版本 + 项目依赖 + 虚拟环境 + 锁文件 + 命令运行</p>
    </div>
    <code>uv python · uv add · uv sync · uv lock · uv run</code>
  </div>
</div>

这不等于“以后所有项目都必须删掉 pip、pyenv”。更准确的理解是：

- `uv python` 覆盖了很多 Python 版本管理场景，也能识别系统里已有的 Python；它还支持 `.python-version`。
- `uv` 项目会使用项目根目录下的 `.venv`，承担传统 `venv` 的隔离职责。
- `uv add` / `uv remove` 面向“项目依赖”，而 `uv pip` 提供的是兼容 pip / pip-tools 风格的接口。
- `uv.lock` 承担可复现依赖锁定的职责，而且是跨平台锁文件。

如果是一个新项目，优先学 **uv 的项目模式**，通常比先学一套 pip + venv + pip-tools 组合更容易形成完整直觉。

## 从零创建一个真正能跑的项目

下面只用一个 `uv-demo` 项目贯穿全文。示例以 Windows PowerShell 为主；除安装命令和路径写法外，大多数 uv 命令在 macOS / Linux 上完全相同。

<div class="uv-subhead"><span>STEP 01</span><strong>安装 uv</strong></div>

官方 standalone installer 在 PowerShell 中可以这样执行：

```powershell
powershell -ExecutionPolicy ByPass -c "irm https://astral.sh/uv/install.ps1 | iex"
```

安装后重新打开 PowerShell，确认版本：

```powershell
uv self version
```

也可以使用 WinGet：

```powershell
winget install --id=astral-sh.uv -e
```

如果 uv 是通过包管理器安装的，后续升级通常也应该继续交给对应包管理器；`uv self update` 更适合 standalone installer 安装的 uv。

<div class="uv-subhead"><span>STEP 02</span><strong>看看 uv 能找到哪些 Python</strong></div>

```powershell
uv python list
```

这个列表不只是在看“uv 自己装过什么”。uv 会同时处理自己管理的 Python 和系统里可发现的 Python。

只想看已经安装的版本：

```powershell
uv python list --only-installed
```

如果需要 Python 3.12：

```powershell
uv python install 3.12
```

`3.12` 表示安装当前 uv 版本可用的最新 3.12 补丁版本；如果项目必须精确到补丁版本，也可以写完整版本号。实际上 uv 在找不到合适的 Python 时也可以按需自动下载，这里显式执行 `uv python install`，是为了先把“解释器”和“项目依赖”两层看清楚。

<div class="uv-subhead"><span>STEP 03</span><strong>创建项目，并固定 Python 版本</strong></div>

当前 uv 0.12 默认的 `uv init` 会创建带构建系统的 package 项目。对第一次学习项目环境的人来说，我们先用更直接的 `main.py` 结构：

```powershell
uv init --no-package uv-demo
cd uv-demo
uv python pin 3.12
```

`uv python pin 3.12` 会把版本要求写进 `.python-version`。以后 uv 在这个项目里执行命令时，就知道应该优先使用哪个 Python。

此时项目大致是：

```text
uv-demo/
├── .python-version
├── README.md
├── main.py
└── pyproject.toml
```

你会发现现在还不一定有 `.venv` 和 `uv.lock`。这是正常的：uv 会在第一次真正需要同步或运行项目时再创建它们。

<div class="uv-subhead"><span>STEP 04</span><strong>给项目添加依赖</strong></div>

我们一次加入两个常见包：

```powershell
uv add requests pandas
```

这条命令不只是“把两个包装进电脑”。它会同时完成三件重要的事：

<div class="uv-action-strip" aria-label="uv add 执行后的三个变化">
  <div><b>1</b><strong>更新声明</strong><code>pyproject.toml</code><span>记录项目需要 requests / pandas</span></div>
  <i>→</i>
  <div><b>2</b><strong>更新锁文件</strong><code>uv.lock</code><span>解析出完整、精确的依赖版本</span></div>
  <i>→</i>
  <div><b>3</b><strong>同步环境</strong><code>.venv/</code><span>让本机环境与项目要求一致</span></div>
</div>

这就是 `uv add` 和“随手往某个环境里 `pip install`”最大的思维差异：**它是在修改项目状态，而不只是修改当前电脑。**

<div class="uv-subhead"><span>STEP 05</span><strong>写一个连续的小例子</strong></div>

把 `main.py` 改成：

```python
import pandas as pd
import requests


orders = [
    {"sku": "K161", "sales": 129},
    {"sku": "K162", "sales": 88},
]

df = pd.DataFrame(orders)

print("总销售额:", df["sales"].sum())
print("requests 版本:", requests.__version__)
```

不用先激活 `.venv`，直接运行：

```powershell
uv run main.py
```

你也可以写得更显式：

```powershell
uv run python main.py
```

两种写法都能让程序在项目环境里执行。

<div class="uv-subhead"><span>STEP 06</span><strong>为什么 <code>uv run</code> 不需要先激活虚拟环境</strong></div>

这是 uv 项目模式最值得建立的新直觉。

<div class="uv-run-flow" aria-label="uv run 自动检查锁文件和虚拟环境的过程">
  <div class="uv-run-command"><code>uv run main.py</code></div>
  <div class="uv-run-checks">
    <div><span>CHECK 01</span><strong>pyproject.toml 变了吗？</strong><p>需要时自动重新锁定。</p></div>
    <div><span>CHECK 02</span><strong>uv.lock 是最新的吗？</strong><p>保证依赖解析状态一致。</p></div>
    <div><span>CHECK 03</span><strong>.venv 同步了吗？</strong><p>不存在就创建，过期就同步。</p></div>
  </div>
  <div class="uv-run-result"><span>RUN</span><strong>在项目环境里执行命令</strong></div>
</div>

传统流程经常写成：

```powershell
python -m venv .venv
.venv\Scripts\Activate.ps1
pip install -r requirements.txt
python main.py
```

uv 项目里，正常开发更接近：

```powershell
uv add requests pandas
uv run main.py
```

`.venv` 仍然存在，只是你通常不用把“手动创建 → 手动激活 → 再确认 pip 指向哪里”当成每天的固定动作。

## `pyproject.toml`、`uv.lock`、`.venv` 到底各管什么

这三个名字第一次出现时最容易混。

<div class="uv-file-cards" aria-label="Python uv 项目三个核心文件和目录">
  <div>
    <span>你维护</span>
    <code>pyproject.toml</code>
    <strong>“项目需要什么”</strong>
    <p>项目元信息、Python 版本要求、直接依赖等都写在这里。`uv add` 会帮你更新它。</p>
  </div>
  <div class="is-lock">
    <span>uv 维护 · 应提交 Git</span>
    <code>uv.lock</code>
    <strong>“最后到底装哪个版本”</strong>
    <p>包含直接依赖和间接依赖的精确解析结果。团队协作时，它让不同电脑更容易得到同一套环境。</p>
  </div>
  <div>
    <span>uv 维护 · 不提交 Git</span>
    <code>.venv/</code>
    <strong>“这台电脑实际装好的环境”</strong>
    <p>它是可重建的本地结果。换电脑时不复制 `.venv`，重新 `uv sync` 即可。</p>
  </div>
</div>

再加上 `.python-version`，四者可以记成：

```text
.python-version  → 我希望用哪个 Python
pyproject.toml    → 我需要哪些直接依赖
uv.lock           → 这些依赖最终解析成哪些精确版本
.venv/            → 当前电脑照着锁文件装出来的环境
```

## `uv lock` 和 `uv sync` 要不要每天手动执行

通常不用。

uv 的项目工作流会自动 lock 和 sync。比如：

- `uv add pandas` 会更新项目依赖、锁文件和环境。
- `uv remove pandas` 也会同步更新这些状态。
- `uv run ...` 运行前会检查锁文件和项目环境是否需要更新。

所以 `uv lock`、`uv sync` 更适合明确场景，而不是形成“每改一行代码就手动执行一次”的习惯。

<div class="uv-subhead is-compact"><span>WHEN</span><strong>什么时候用 <code>uv lock</code></strong></div>

只想更新或确认锁文件，不准备运行程序：

```powershell
uv lock
```

例如修改了依赖声明后，希望先得到新的锁文件再提交。

<div class="uv-subhead is-compact"><span>WHEN</span><strong>什么时候用 <code>uv sync</code></strong></div>

刚把团队项目拉到新电脑，希望把本地环境建立好：

```powershell
git clone <repo>
cd <repo>
uv sync
```

也很适合先给编辑器准备好 `.venv`，然后再开始开发。

这也是团队项目为什么应该提交 `uv.lock`：**依赖声明只是范围，锁文件才记录当时真正解析出的完整版本集合。**

## `uv add` 和 `uv pip install` 到底怎么选

这是从旧 pip 工作流迁移时最重要的分界。

<div class="uv-choice" aria-label="uv add 与 uv pip install 使用场景对比">
  <div class="is-primary">
    <span>新项目 / 正常项目开发</span>
    <code>uv add requests</code>
    <strong>优先用这个</strong>
    <p>它会把依赖写进 `pyproject.toml`，并更新 `uv.lock` 与项目环境。下次换电脑仍然知道项目需要它。</p>
  </div>
  <div>
    <span>兼容旧 pip 工作流</span>
    <code>uv pip install requests</code>
    <strong>直接操作环境</strong>
    <p>它更像 pip：把包装进某个环境，但不会替你把这个依赖持久化为项目声明。适合 requirements 工作流、临时环境或明确知道自己在做什么的场景。</p>
  </div>
</div>

官方也明确建议：在 uv 管理的项目中，不要把 `uv pip install` 当成项目依赖管理的常规方式。要把依赖真正加入项目，使用 `uv add`。

## 查看依赖、删除依赖、导出 requirements

看当前项目的依赖树：

```powershell
uv tree
```

如果不再需要 `requests`：

```powershell
uv remove requests
```

如果外部系统仍要求传统 `requirements.txt`，不要手工复制 `uv.lock`，直接导出：

```powershell
uv export --format requirements.txt --output-file requirements.txt
```

这里要分清“项目的事实标准”和“兼容输出”：

```text
pyproject.toml + uv.lock
        │
        ├── uv 自己管理项目时直接使用
        │
        └── uv export → requirements.txt
                       给旧部署系统 / 其他工具兼容使用
```

如果团队已经全面使用 uv，就没有必要仅仅因为“以前都这么做”而额外维护一份手写的 requirements。

到这里，新手真正应该记住的不是 40 条命令，而是下面这条链：

## 那些值得知道，但不必放在主流程里的命令

旧笔记里还有很多命令是有效的，但它们不适合和日常项目流程放在同一层级。

| 场景 | 命令 | 什么时候再用 |
| --- | --- | --- |
| 手动创建虚拟环境 | `uv venv` | 你明确在做非项目式环境管理时 |
| requirements 兼容 | `uv pip install -r requirements.txt` | 老项目仍以 requirements 为中心时 |
| requirements 严格同步 | `uv pip sync requirements.txt` | 继续沿用 pip-tools 风格工作流时 |
| 临时运行工具 | `uvx ruff check .` | 想运行 CLI 工具，但不想装进项目依赖时 |
| 安装全局 CLI 工具 | `uv tool install ruff` | 工具希望长期作为用户级命令使用时 |
| 缓存清理 | `uv cache prune` / `uv cache clean` | 排查缓存或确实需要释放空间时 |
| 更新 standalone uv | `uv self update` | uv 由官方 standalone installer 安装时 |

这些命令不是“不重要”，只是新手在还没搞清项目主线之前，不需要先背。

## 最后再排除几个常见误区

<div class="uv-mistakes" aria-label="使用 uv 时常见的四个误区">
  <div><span>误区 1</span><strong>“装了 uv 就等于装了 Python”</strong><p>不是。uv 是工具；Python 解释器仍然是另一层，只是 uv 可以帮你下载安装。</p></div>
  <div><span>误区 2</span><strong>“有 .venv 就必须先 activate”</strong><p>不是。uv 项目推荐直接 `uv run`；激活只是可选用法。</p></div>
  <div><span>误区 3</span><strong>“uv add 就是更快的 pip install”</strong><p>不完全是。`uv add` 同时修改项目依赖声明、锁文件和环境。</p></div>
  <div><span>误区 4</span><strong>“requirements.txt 才是团队依赖的唯一标准”</strong><p>在 uv 项目里，`pyproject.toml + uv.lock` 已经能形成完整、可复现的项目依赖状态；requirements 可以按需导出。</p></div>
</div>

如果只想记一句话：**新项目先用 uv 的项目工作流，而不是把旧的 pip + venv 操作逐条翻译成 uv 命令。**

这样你真正得到的不是一张新的命令速查表，而是一套从“这份代码需要什么”到“这份代码怎样稳定运行”的完整项目管理方式。
