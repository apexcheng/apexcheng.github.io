# 博客写作规则

本文件负责文章内容质量、事实与示例、frontmatter 填写、分类应用和完稿检查。目录、公开状态默认值、索引更新及按需读取入口以 `AGENTS.md` 为准。视觉设计没有统一模板，`docs/ARTICLE_VISUAL_SYSTEM.md` 和 `docs/MDX_PATTERN_LIBRARY.md` 仅供自愿参考。

## 最高优先级风格参考：ChatGPT 日常回复风格

博客的文字表达和信息组织，优先参考 ChatGPT 在日常问题解答中呈现的风格。这是全站最高优先级的风格参考；当旧文章、Demo、视觉模式库、模板惯例或其他一般性建议与它冲突时，优先采用这里的原则。

### 文字表达

- **先给结论，再解释依据**：让读者尽快知道核心答案，再逐步说明原理、过程、原因、影响和适用边界；需要悬念或叙事铺垫时，可根据主题调整顺序。
- **自然、通俗、准确**：使用清楚的日常语言，不刻意学术化，不堆砌术语；必要术语首次出现时，用普通读者能理解的话解释。
- **逻辑清楚，层次分明**：一段围绕一个主要意思展开；复杂问题拆成容易跟进的步骤，避免突然跳结论或让读者自行补齐关键前提。
- **解释过程，而不只报结果**：适合时说明实际如何运作、为什么会出现不同结果，以及它们分别有什么影响。
- **用例子帮助理解**：优先使用具体场景、数字、对比和类比解释抽象内容；例子必须自洽，并标明教学构造数据或假设情境。
- **明确认知边界**：区分已确认事实、合理推测、个人观点和改进建议；证据不足时说明不确定性。
- **有判断，不迎合**：发现逻辑矛盾、事实错误或更合理的解释时直接指出，并给出理由；批评针对观点、行为和机制，不做人身攻击。
- **简洁但不省略必要解释**：不重复、不凑篇幅、不堆空泛总结；也不为了短而省略读者理解问题所必需的信息。

### 信息组织

- 标题和小标题应帮助读者定位内容，不为凑层级而拆分章节。
- 并列内容适合使用列表；多方案、多维度比较适合使用表格；步骤、关系和机制可按需使用流程图、示意图或代码。
- 加粗、引用、提示块和结论强调只用于真正重要的内容，不机械制造视觉焦点。
- 复杂内容先建立整体理解，再展开必要细节；简单内容直接说清，不强行套用复杂结构。
- 总结、结论框和行动建议按内容需要决定，不要求每篇文章或每一节都设置。

### 视觉与阅读体验

- 借鉴回复中清晰的层级、自然的阅读节奏、适当的信息密度和容易定位重点的组织方式，不照搬聊天窗口、消息气泡或固定 Markdown 排版。
- 视觉形式由文章主题决定，可以使用杂志排版、技术手册、数据故事、交互演示、图解或其他设计；不能为了模仿回复风格而牺牲文章自身的表现力。
- 避免无意义的卡片、边框、渐变、装饰和重复强调；需要时可以大胆使用，不设数量或形式限制。

这套风格是表达和理解的优先参考，不是固定文章模板。文章可以因题材采用不同叙事方式、语气和视觉语言；只要不损害准确性与理解效果，就不必强行统一。

## 内容原则

1. 不虚构作者经历、项目结果、数据或第一人称判断；为教学构造的示例须明确标注。
2. 作者提供的事实、Agent 推断和外部资料要能区分；不确定内容明确标注。
3. 保留真实场景、失败、取舍和边界，避免正确但空泛的总结。
4. 默认专业但通俗：优先使用日常语言、具体对象和真实场景解释概念；必要术语首次出现时，用目标读者能理解的话说明。
5. 独立审查须区分**已核实问题、待核实疑点和优化建议**；无法访问来源或链接形式不常见，不等于内容错误或链接失效。重要事实与引用应以可核查证据为准，未核实的结论不得当作确定错误。

## 读者视角写作

正式文章默认面向最终读者，而不是面向作者、Agent 或当前协作会话。文章结构和表达应从“读者需要知道什么、按什么顺序最容易理解”出发，而不是复述 Agent 的分析、执行和决策过程。

- 不把 Prompt、任务拆解、需求确认、内部推理、修改过程或 Agent 自我说明写进正文，除非这些内容本身就是文章主题。
- 避免保留“我来分析”“本次任务”“根据用户要求”“Agent 需要”等描述协作过程的表达。
- 需要解释方案取舍时，直接说明问题、原因、选择、结果和边界，不描述 Agent 是怎样思考出来的。
- 第一人称只用于作者真实经历、判断和实践，不由 Agent 代替作者制造经历或观点。
- 判断一段内容是否应该保留时，问：**如果读者完全不知道这篇文章是由 AI 协助整理的，这段内容是否仍然有价值？** 如果没有，应删除或改写。

## Frontmatter

新文章从 `templates/post.mdx` 开始，字段类型以 `src/content.config.ts` 为准；下表规定填写约定。

| 字段 | 规则 |
| --- | --- |
| `title`、`description` | 必填，直接说明主题和价值 |
| `date` | 使用 `YYYY-MM-DDTHH:mm:ss+08:00` |
| `updated` | 可选，存在时使用相同格式 |
| `category` | 只能使用固定分类 |
| `tags` | 使用具体主题词 |
| `minutes` | 使用合理的阅读时间整数 |
| `featured` | 默认 `false` |
| `pinned` | 默认 `false`；设为 `true` 时在文章列表页置顶 |
| `archived` | 默认 `false`；设为 `true` 时保留原文章 URL，但退出默认列表、首页、系列阅读路线、站内搜索、RSS 等推荐入口；文章列表可勾选「包含已归档」查看 |
| `series`、`seriesOrder` | 可选；进入系列时两个字段同时填写，顺序使用正整数 |
| `draft`、`private` | 新文章默认值遵循 `AGENTS.md`；不因普通内容编辑改变已有文章的公开状态 |

`private: true` 只表示不进入公开页面和索引，不是密码保护。

`archived: true` 不是删除或私密保护；知道原链接的读者仍可访问，搜索引擎也可能通过外部链接找到文章。永久删除文章需单独处理源码及已有引用，不提供网页删除按钮。

草稿和私密文章在公开前不要求进入内容索引。

## 分类

| 分类 | 使用场景 |
| --- | --- |
| `技术` | AI、Agent、编程、工具开发、软件架构、自动化原理、基础设施、Excel 函数技术 |
| `经营与数据` | 电商运营、经营分析、利润核算、报表建模、业务流程和产品体验改善 |
| `生活与思考` | 职场、健康、消费、社会事件、个人财务和观点反思 |
| `视觉实验室` | 独立实验区：组件、交互、图表和文章展示方式 Demo |

分类按文章主要回答的问题所属领域确定，与教程/实践等写作形式无关。技术教程、技术复盘同属「技术」；用技术改善经营流程、核算或管理的文章归「经营与数据」。专题系列独立于分类。

标签优先从 `src/data/tags.ts` 的标准标签词表选择，通常每篇 1～3 个；只保留真正帮助跨文章导航的主题词，单篇文章里的技术名词交给全文搜索。非同义标签按文章主旨选择，不做机械全文替换。

## 工作方式

### 小范围修改

改字、事实修正、链接、frontmatter 和局部小改直接执行：

- 只读目标文章和必要上下文。
- 不重新规划全文。
- 不读取视觉模式库或 Demo。

### 新文章或结构性重写

根据主题、读者和文章目标，自主决定叙述方式、章节结构、文风及视觉表达。可以使用递进论述，也可以采用故事、访谈、问答、案例、时间线、教程、观点评论或其他合适结构。视觉资料和旧文章均为可选参考，不要求先完成固定设计流程。

### 解释性文章的递进论述

以下是解释复杂概念、指标、模型或预测时可参考的组织方法，不是固定章节模板。根据文章主题选择需要说明的内容：

1. **场景与问题**：交代要解决的问题，以及必要的对象、时间和使用场景。
2. **来源与口径**：关键事实和数字给出可定位的来源或作者提供的依据；定义、变量和计算规则在使用前说明。涉及指标时，交代统计对象、周期、单位及筛选范围；比例还需说明分子和分母。来源无法核实时明确标注，不补造出处。
3. **推导与应用**：展示事实怎样经过计算、筛选或判断得到结果；复杂过程用少量中间状态衔接，不只列公式和结论。
4. **结果与边界**：解释结果能支持什么判断；区分原始事实、据实计算的指标、暂估与未来预测。预测需说明依据、假设和时间范围；缺失值不能当作零，缺少预测依据时不能把历史指标直接当作未来结果。限制应在影响理解或使用的位置出现，不只留到文末。

不涉及数据或预测的文章无需补齐这些项目。观点文章可以从反例或故事展开，教程可以先给可运行示例；以内容本身最自然、读者最容易理解为准。

**例子的自洽性**：同一示例的初始值、过程和结论必须一致，比例可复算，记录所属周期与观察时间可区分；改变假设时明确指出。教学示例说明推导，不据此宣称真实效果或预测准确率。使用生活类比时，说明与原模型的对应关系及关键差异。

### 视觉强调与观点表达

是否使用观点锚点、彩色高亮、加粗、结论块、图表或其他视觉强调，由文章内容和整体设计决定。可以大量使用，也可以完全不用；不要求每篇文章寻找或突出特定句子。表达鲜明观点时，仍应有事实和推导支撑，避免虚构动机、夸大比例、绝对化结论或人身攻击。

参考旧文、组件、模式或 Demo 时，按 `AGENTS.md` 的路由读取，不为完成写作默认遍历资料。

## 静态文件

下载文件放在 `public/files/`，文章使用 `/files/` 链接。这里是公开文件目录，不能放私密资料、账号、token 或其他敏感文件；private 文章不等于 private 文件。

## 完稿读者体验审查

新增文章、结构性重写或较大文章改造完成后，必须以“第一次看到这篇文章的目标读者”身份重新通读全文。局部修正只复核受影响内容；是否需要浏览页面，按下节的页面检查范围执行。

### 内容理解

- 阅读顺序是否自然，关键结论是否在合适的位置出现。
- 新概念、术语、变量、公式和业务口径是否在第一次出现时能被理解。
- 是否存在逻辑跳跃、突然出现的数字或前提、重复解释和信息过载。
- 示例是否能独立跑通，读者能否从输入一路看懂到结果。
- 主线和扩展内容是否分层清楚，重点是否足够突出。

涉及视觉表达时，检查实际页面是否准确传达内容、是否适合主题、阅读和交互是否顺畅；不以是否符合旧有风格或组件模式作为审查标准。

## 最小发布检查

文章创建或编辑完成后：

1. frontmatter 符合字段约定，公开状态符合用户要求和 `AGENTS.md`。
2. 没有模板占位词和明显敏感信息。
3. 运行当前环境中可用的相关测试或构建；不可运行时直接说明。

涉及页面布局、视觉结构、交互或文章专属 CSS 时，按改动范围检查相关页面和设备尺寸；发现问题后修正并复查。无法浏览时报告未验范围，不把静态阅读或构建通过视为页面验收通过。仅修改规则文档时，验证按 `docs/DEV_RULES.md` 执行。
